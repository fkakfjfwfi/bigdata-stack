09 · Hive 存储压缩与优化

这是全课程的压轴。前面八章讲"怎么用"，这一章讲"怎么让它快"。优化的顺序有讲究：先改存储格式（改一行建表语句，省 85% 空间且不损失速度），再治理小文件，然后才是调参数和改 SQL。反过来做（一上来就调参数）往往白忙——因为瓶颈根本不在那儿。这一章还给了一组实测数字，比任何"建议"都有说服力。

内容基准 主体素材：Hadoop 实战课第 16 天（20 个有效视频，另有 1 个"回顾"已跳过）　·　2026-11 提炼 需留意：9.3 的实测数字来自课程环境（Hive 3.1.2 + 18.13 MB 样本），倍数会随数据特征变化，但"ORC 显著小于 TEXTFILE、且查询不变慢"这个结论是稳定的；9.9 的 JVM 重用在新版本里价值已下降（Tez/Uber 模式的普及），照做前先确认你的执行引擎。

9.1 一条 SQL 怎么变成作业

优化要先知道"钱花在哪"。Hive 收到一条 SQL 会经过四个组件：

SQL → 解释器（Parser）→ 编译器（Compiler）→ 优化器（Optimizer）→ 执行器（Executor）
       语法树            逻辑计划          物理计划（选 join 顺序、选执行引擎）   提交作业

各子句落到哪个阶段

SQL 子句变成什么代价
WHEREMap 端过滤（谓词下推后连数据都不读）低
SELECT 少量列列裁剪（列式存储只读这几列）低
GROUP BYMap 预聚合 → 按 group key shuffle → Reduce 聚合高（shuffle）
JOIN两表按 join key shuffle，或小表广播成 Map Join最高
ORDER BY收成 1 个 Reduce 全局排序极高
LIMIT各 Map 各取 N 条即可，不需要 Reduce低
优化的本质就一句话：少读数据、少 shuffle。

表里六个子句，只有 GROUP BY、JOIN、ORDER BY 会产生 shuffle——它们对应 MR 里的分区和排序，要落磁盘、走网络。而 WHERE 和列裁剪之所以最划算，是因为它们让数据"压根不进内存"。

所以优化优先级是：能不读的别读（分区/列裁剪/谓词下推）＞ 能少搬的少搬（Map Join / 减少 reduce）＞ 最后才调参数。

还有一种情况：压根不起作业。简单查询（select * from t limit 10）会走 fetch task，直接从 HDFS 读文件返回，不提交 MR——这就是为什么有些查询"秒回"。判断标准在后面 9.9 讲。

9.2 存储格式：行式与列式

这是优化里性价比最高的一步——只改建表语句里的一个词，不用改任何 SQL。

行式 vs 列式：本质差别在哪

行式（TEXTFILE）——按行连续存
[id=1, name=张三, age=20] [id=2, name=李四, age=21] [id=3, ...]

列式（ORC / PARQUET）——按列分别存
id:   1, 2, 3, ...
name: 张三, 李四, 王五, ...
age:  20, 21, 22, ...
差别只在"只查少数几列"时才爆发。

SELECT age FROM t WHERE age > 20——行式必须把每行的 id、name 全读出来再丢掉（IO 浪费）；列式只读 age 那一列，其余列的字节一个都不碰。这叫列裁剪（Column Pruning）。

反过来，SELECT * FROM t（取所有列）时列式没优势——这也是为什么下一节那个 count(*) 实验里，三种格式耗时一样。

五种格式对比

格式行/列特点用在哪
TEXTFILE行式纯文本、人可读、不压缩；唯一能直接 LOAD DATA 的格式ODS 贴源层、要看原始数据时
ORC列式（stripe 内按列）Hive 自家造的，压缩率最高、带索引、支持矢量化Hive 数仓默认选它
PARQUET列式压缩率略低于 ORC，但生态最广（Spark / Presto / Impala 都友好）Spark 为主的项目
SEQUENCEFILE行式（二进制 KV）Hadoop 早期格式，现在主要用来合并小文件小文件治理
AVRO行式带 schema，适合写多读少的场景少见
ORC / PARQUET 都不能 LOAD DATA，只能 INSERT ... SELECT。

因为要经过编码/序列化，纯文件搬移做不到。所以标准流程是：先建 TEXTFILE 表 LOAD DATA 灌数据，再 INSERT INTO ... SELECT 导进 ORC 表。

这是实操里最容易卡住的地方——直接往 ORC 表 LOAD DATA 会报错或数据读不出来。

ORC 的特殊结构：stripe

ORC 文件
├── Stripe 1（默认 250 MB）→ 内部按列存
├── Stripe 2
├── ...
└── 文件尾部 metadata（行组索引就存在这里）

ORC 是"有行有列"：先按 stripe 横向切（一行记录不会跨 stripe），stripe 内部再按列纵向存。这个设计是下一节两级索引的基础——索引建在 stripe 上。

（03 · 全篇；行式列式的读放大解释为补充）

9.3 实测：18.13 MB 数据，三种格式打一架

课程做了一个很干净的对照实验：三张表结构完全一样，唯一差别是 STORED AS 后面那个词，灌同一份 18.13 MB 的数据。

体积对比

存储格式HDFS 实际占用相对原始压缩倍数
TEXTFILE18.13 MB100%1.0×（完全不压）
PARQUET13.09 MB72%1.39×
ORC（默认 ZLIB）2.78 MB15%6.5×
ORC 比 TEXTFILE 省了 85% 存储，比 PARQUET 又小 4.7 倍。同一份数据、同样的 SQL、只改建表语句里的一个词。

查询耗时对比

表select count(*) 耗时
log_text约 23 秒
log_orc约 23 秒
log_parquet约 23 秒

三者基本一样。老师当场强调了这个"很神奇的事"：文件小了 6 倍，查询速度却没变慢——说明 ORC 压缩不牺牲查询性能，纯粹是白赚的存储。

但要注意：count(*) 看不出列式存储的真正优势。

count(*) 要读所有列（甚至只读行数也行），列裁剪完全用不上。真正体现差距的是"只查少数几列"的查询——那种情况下 ORC 可能快几十倍，因为它的 IO 量只有行式的几分之一。

所以别拿 count(*) 的耗时去说服别人"列式没用"，选错了测试用例。

ORC 的三个压缩档位

同一份数据，ORC 内部还能再分三档（课程实测）：

配置体积说明
只列式编码、不压缩7.73 MBSTORED AS ORC 但关掉压缩
ZLIB（默认）2.78 MB压缩率高，速度慢一些
SNAPPY3.78 MB压缩率略低，速度快
STORED AS ORC 和 orc.compress 是两件事。

前者只做"列式编码"（7.73 MB），后者决定用什么算法（ZLIB 得 2.78、SNAPPY 得 3.78）。不指定算法不等于不压缩——ORC 默认就用 ZLIB。

9.4 压缩与切片的矛盾

选压缩算法时，很多人只看"压缩比"。但有一个更硬的约束：能不能切片（splittable）。

算法压缩比速度可切片用途
Gzip高中等偏慢否归档、冷数据
Bzip2最高最慢否极少用
LZO中快是（需建索引）曾经的主流
Snappy中（略低于 Gzip）极快是生产首选
ZLIB高慢是ORC 默认
为什么"可切片"这么重要——这条因果链必须讲清：

① HDFS 上的文件要交给 Map 处理，每个 Map 处理一个"切片"。
② 压缩文件如果不可切，整个文件只能由一个 Map 处理——一个 10 GB 的 gzip 文件，就只有一个 Map 在跑，集群有 100 台机器也帮不上忙。
③ 所以 Snappy 的压缩率不是最高的，但它是生产首选——因为它可切分，能把大文件拆给多个 Map 并行处理。

结论：选压缩算法时，先问"能不能切"，再问"压得狠不狠"。压缩比高但不可切，在大数据场景下是负优化。

反过来说：如果文件本身很小（小于一个块），或者不参与并行计算（只归档），那 Gzip 的高压缩比就有价值了。所以选型要看场景，不是一刀切。

（05 · 07:51–11:00；07 · 04:55）

9.5 ORC 两级索引：为什么能"跳过 99% 的数据"

这是全章最有技术含量的部分，也是 ORC 比 PARQUET 更快的关键。

行组索引（Stripe Index）：管范围查询

原理：ORC 写每个 stripe 时会记录该 stripe 内每列的 min / max / 行数 / 是否有 null，存在文件尾部。查询时先读这些统计，判断"这个 stripe 里根本不可能有我要的值"，直接跳过不读。

Stripe 1: id  1 ~ 25
Stripe 2: id 26 ~ 50      ← 只有它可能命中
Stripe 3: id 51 ~ 75
Stripe 4: id 76 ~ 100

select * from log_orc where id >= 30 and id <= 40;
→ 只读 Stripe 2，其余 3 个直接跳过（IO 降到 1/4）

关键：这是 IO 层面的跳过——不是"读完再过滤"，是压根不读。所以 stripe 越多（文件越大）、过滤条件越窄，效果越明显。

布隆索引（Bloom Filter）：管等值查询

原理：在指定列上建布隆过滤器，能快速判断"这个 stripe 里肯定没有值 X"，从而跳过。

布隆过滤器的关键特性：可能误判"存在"，但绝不误判"不存在"。

所以它给出的结论只有两种：
· "肯定没有" → 可靠，可以安全跳过这个 stripe；
· "可能存在" → 不可靠，还得真去读一下确认。

正因为"证伪可靠、证真不可靠"，它才能安全地用在查询优化上——跳过的一定是对的，没跳过的只是多读了一点，不影响结果正确性。这是它能在数据库里被广泛使用的根本原因。

两者的分工

索引适合判断依据怎么用
行组索引范围查询（>、<、BETWEEN）min / max 与查询区间是否相交默认就有（写文件时自动记录）
布隆索引等值查询（=、IN）值是否可能在这个 stripe 里要显式建：建表时指定 'orc.bloom.filter.columns'='col1,col2'

记忆：范围靠 min/max（免费的），等值靠布隆（要显式建）。

矢量化查询

一次处理一批（默认 1024 行）而不是一行，减少函数调用开销，还能利用 CPU 的 SIMD 指令。

为什么只有列式存储才能矢量化：因为要"一次拿 1024 个同类型的值放进数组"，这要求这些值在磁盘上是连续存放的——列式天然满足，行式做不到（行式的 1024 行是交错的）。

开关：hive.vectorized.execution.enabled（Hive 2 之后默认开）。

（09、10、11 三集；布隆特性的解释为补充）

9.6 小文件治理

第 02 章算过那笔账：每个文件在 NameNode 内存里约 150 字节，而 NameNode 的堆是有限的。千万级小文件就会把堆吃干。

但小文件在这里还有第二重浪费：

浪费说明
NameNode 内存150 字节/文件，百万文件就是几百 MB 常驻堆
Map 任务数一个文件至少一个 Map——100 万个 1 KB 的文件要起 100 万个 Map 任务，每个任务的启动开销（几秒）远超处理那 1 KB 的收益

四种解法

手段怎么做适用
写入后自动合并hive.merge.mapfiles=true（只有 Map 任务时合并）
hive.merge.mapredfiles=true（有 Reduce 时也合并）
hive.merge.smallfiles.avgsize 设阈值		常规写入，最省事
调 reduce 数输出文件数 = reduce 数，SET mapreduce.job.reduces=N能预估输出规模时
DISTRIBUTE BY 控制分区按某列分发，输出文件数 = 该列的不同值个数想要"一类一个文件"
CONCATENATEALTER TABLE t CONCATENATE;只对 ORC / RCFile 有效，TEXTFILE 不行
两个容易忽略的点：

① hive.merge.mapfiles 只在纯 Map 任务时生效。如果你的作业有 Reduce 阶段，光开这个没用，必须开 hive.merge.mapredfiles。

② CONCATENATE 是元数据层面把多个小文件"逻辑拼接"成一个大文件（对 ORC 可行，因为 ORC 的 stripe 可以独立拼接），不重写数据，所以很快。但它对 TEXTFILE 无效——文本文件没法这么拼。

9.7 两种 JOIN：差在要不要 shuffle

JOIN 是 Hive 里最贵的操作，而它有两种截然不同的实现，代价差一个数量级。

Map JoinReduce Join（Common Join）
怎么做小表广播到每个 Map 节点，在内存里建哈希表，边读大表边匹配两表都按 join key 做 shuffle，相同 key 进同一个 Reduce 再拼
有 shuffle 吗没有有（磁盘 + 网络双份开销）
前提小表能装进内存（默认 25 MB）无（任何规模都能跑）
快慢快一个数量级慢
怎么触发hive.auto.convert.join=true（默认开）；小表写在前面；或用 /*+ MAPJOIN(小表) */自动降级

Reduce Join 的底细：一个 tag 字段撑起整个 join

课程讲了这个机制，理解了它才知道 shuffle 贵在哪：

两表在 Map 阶段各自打上来源标签：
  A 表：<key, (A, 其他字段)>
  B 表：<key, (B, 其他字段)>
        ↓ 按 key shuffle（落磁盘 + 走网络）
  Reduce 收到同一个 key 的全部记录，按 tag 分成两堆
        ↓
  两堆做笛卡尔积拼出结果
所以 Reduce Join 的本质是：用 shuffle 把"同一个 key 的两边记录"搬到一起，再用一个 tag 字段区分来源。

贵的原因很具体——两表的数据都要完整地过一次磁盘和网络。10 GB 对 10 GB 的 join，至少要写 20 GB 临时文件再读回来。

这也解释了为什么要做 bucket map join（第 04 章 4.9）：如果两表按 join key 分桶且桶数相同，同 key 天然在同一个桶，就不用全量 shuffle 了，直接桶对桶。

大表 join 大表怎么办

方案前提
Bucket Map Join两表按 join key 分桶、桶数相同（或整数倍），小表桶能装进内存
SMB Join（Sort-Merge-Bucket）在上面的基础上再按同列 SORTED BY，可以归并而不用建哈希表 —— Hive 里最快的 join
加大内存让 Map Join 能装下调 hive.mapjoin.smalltable.filesize，但受物理内存限制
接受 Reduce Join实在没条件时，只能优化 reduce 数、处理倾斜

（15、16 两集；桶 join 见第 04 章 4.9）

9.8 Group By 原理与数据倾斜

三阶段

Map 端预聚合（Combiner）
   ↓ 按 group key 分区
Reduce 端聚合

Map 端预聚合是关键——如果 group key 重复度高（比如按城市分组，全国就几百个城市），Map 端就能把几百万行压成几百行再发出去，shuffle 数据量降几个数量级。

倾斜：某个 key 太多

表现：8088 里大部分 reduce 已完成，剩一两个卡在 99% 长时间不动。

原因：某个 key 的记录数远超其他（比如 NULL、空串、默认值 -1、某个爆款商品）。按 key 分区后，全落到同一个 Reduce，一台机器干所有活。

两阶段聚合：Hive 自带的解法

SET hive.groupby.skewindata = true;

开启后 Hive 会把一个作业拆成两个：

阶段做什么
第一个作业给 key 加随机前缀（hadop → 0_hadop、1_hadop…），这样同一个 key 被打散到多个 Reduce 做局部聚合
第二个作业去掉前缀，按原始 key 再做一次聚合，得到最终结果
这就是"加盐打散"的标准实现。代价是多一个作业、多一轮 shuffle，所以只在真倾斜时才开——不倾斜时开了纯属浪费。

但首选不是它

顺序手法为什么
1先查是不是 NULL 造成的很多"倾斜"其实是几百万行 NULL 全落一个 Reduce，加个 WHERE col IS NOT NULL 就好了，比任何参数都简单
2Map Join能绕开 reduce 就绕开
3skewindata 两阶段聚合真倾斜时的通用解
4热点单独处理热点极少但极大时，拎出来单独跑再 union

EXPLAIN SELECT count(*) FROM log_orc;
EXPLAIN EXTENDED ...        -- 更详细（含语法树）
EXPLAIN DEPENDENCY ...      -- 只看读了哪些分区/文件

看什么，四个点：

看判断
有几个 Stage作业被拆成几个 MR。Stage 越多，中间落盘越多
有没有 Reduce只有 Map 阶段的作业快得多（limit 类查询应该只有 Map）
是 Map Join 还是 Reduce Join看到 Map Join Operator 才是好结果

运行时开关

参数作用注意
hive.exec.mode.local.auto本地模式：小数据量时在本地跑，不起集群作业要满足三个条件（输入小、文件数少、reduces 为 1）
hive.exec.parallel并行执行：无依赖的 Stage 一起跑要配 hive.exec.parallel.thread.number；集群忙时开了会抢资源
mapreduce.job.jvm.numtasksJVM 重用：一个 JVM 跑多个 task代价是 task 之间不隔离，一个 OOM 影响其他；现代版本价值已下降
hive.fetch.task.conversionfetch 抓取：简单查询不走 MRmore（默认）比 minimal 覆盖更多查询
hive.stats.autogather自动收集统计信息CBO 依赖它，关掉会导致优化器选错计划

CBO 与那个"反直觉"的例子

CBO（Cost Based Optimizer）= 基于代价选执行计划。它和老的 RBO（规则优化）的区别在于——RBO 只看规则，不看数据分布；CBO 看统计信息。

课程给了一个很好的反例：1000 条数据里 900 条都命中条件时，走索引反而比全表扫慢。

因为走索引要先读索引、再回表取数据，900 次随机 IO 远比一次顺序全表扫慢。RBO 只会机械地认为"有索引就用索引"，而 CBO 会估算"命中率 90% → 全表扫更便宜"。

这也解释了 CBO 的命门：它依赖统计信息的准确性。统计信息过期（数据量大变但没重新 ANALYZE），CBO 就会选错计划——表现是"同一个 SQL 昨天快今天慢"。这时该做的是 ANALYZE TABLE t COMPUTE STATISTICS，而不是改 SQL。

预测执行与 fetch

机制做法代价 / 判断
推测执行
Speculative Execution		某个 task 跑得特别慢时，另起一个同样的 task，谁先完成用谁的结果浪费资源（两个 task 同时跑）。集群资源紧张时应该关掉；数据倾斜导致的慢不要靠它——重跑一次还是慢
fetch task简单查询（无聚合、无 join、无排序）不起 MR，直接从 HDFS 读这就是"为什么有的查询秒回"。select * from t limit 10 属于这类

优化的优先级：这一章的收尾

第一层：少读数据（改一次，长期收益）
分区裁剪（WHERE 带分区字段）→ 列裁剪（别写 SELECT *）→ 谓词下推（过滤条件写在子查询里）→ 换 ORC 格式（省 85% 存储，不用改 SQL）

第二层：少 shuffle（改 SQL 写法）
小表 join 大表走 Map Join（小表写在前面）→ 用 GROUP BY 代替 COUNT(DISTINCT) → 避免 ORDER BY 全局排序 → 大表 join 大表考虑分桶

第三层：治小文件（改写入策略）
开合并参数 → 调 reduce 数 → 用 DISTRIBUTE BY 控制文件数 → CONCATENATE

第四层：调参数（最后才做）
并行执行、JVM 重用、推测执行、skewindata——这些是"锦上添花"，前三层没做好时调它们基本没用

课程里有一句话值得单独记住："先看执行计划，再动手优化。"

不 EXPLAIN 就调参数，等于不看仪表盘修车。而且优化过的 SQL 要再跑一次 EXPLAIN 对比——否则你不知道自己改的那一项到底有没有生效。
