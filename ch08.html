08 · ZooKeeper 与高可用

第 02 章结尾留了一个悬念：NameNode 挂了整个集群就废，而 SecondaryNameNode 兜不住。这一章给出答案——用 ZooKeeper 选主 + JournalNode 共享日志，让两个 NameNode 一主一备自动切换。而 ZooKeeper 本身值得学的不只是"怎么装"，是它怎么把"一个进程还活着"变成树上一个可被监听的状态。这一点想通了，HA 的九个步骤就是它的自然推论。

内容基准 主体素材：Hadoop 实战课第 15 天（19 个有效视频，另有 1 个"回顾"和 1 个"串讲"已跳过；4 个答疑全部保留）　·　2026-11 提炼 需留意：8.6 / 8.7 的配置项名与端口以 Hadoop 3.3.0 为准；8.8 的"8485 连不上"是 JN 启动慢导致的，不是真错误——这类时序问题在不同机器上表现不一，遇到时先等等再看日志。

8.1 为什么需要 ZooKeeper

"分布式协调服务"这个词很抽象。换成具体问题就清楚了——一群机器一起干活，必须先解决四个问题：

问题具体场景ZK 怎么解决
谁当主？两个 NameNode，必须只有一个对外服务抢临时节点，抢到的当主
有人挂了吗？主挂了，备要立刻顶上临时节点随会话消失，备收到通知
配置怎么同步？改一个参数，全集群生效配置放 znode，各节点 watch
怎么互斥？同一时刻只能有一个进程写某个资源分布式锁（临时顺序节点）
一句话定位：ZK 是一个"小而可靠的共享状态存储"，专门用来放"谁活着、谁当主、配置是什么"这类协调信息。

它本身也是个集群（3 台或 5 台），靠过半机制保证一致性——所以它自己不会成为新的单点。这一点很关键：用 ZK 做 HA，前提是 ZK 自己是高可用的。

课程还有一个很实在的提示：ZK 的数据量必须很小（单节点 1 MB 上限）。它是"协调"用的，不是"存储"用的——见过有人往里塞业务数据，那是误用。

（02 · 全篇）

8.2 数据模型与四种节点

ZK 的数据模型是一棵树，类似文件系统。但有一处关键不同：

每个节点（znode）都能存数据，不只是叶子节点。

文件系统里目录只是容器，而 ZK 的每个节点既是"路径"又是"值"。所以 /app/config 这个节点本身就能放一份配置内容。

限制：单节点数据 1 MB 上限；路径用 / 分隔；节点名不能含保留字符。

四种节点类型：2×2 的组合

普通（不加 -s）顺序（-s）
持久（默认）create /path datacreate -s /path data
临时（-e）create -e /path datacreate -e -s /path data

记忆：-e = ephemeral（临时），-s = sequential（顺序），两个可以叠加。什么都不加就是持久普通节点。

类型关键特性用在哪
持久节点一直存在，客户端断开、ZK 重启都不影响；唯一能挂子节点的类型存配置、做目录
临时节点生命周期绑定会话——客户端断开后自动删除；不能有子节点存活探针、选主、分布式锁
顺序节点创建时自动在名字后加递增序号（0000000001…）排队、锁的公平性
临时节点是这一章最值钱的知识点。它把"进程活着"这件事，变成了树上一个可被监听的状态。

想想没有它的时候：你怎么判断另一个进程是否还活着？ping 它？那对方假死怎么办？自己维护心跳表？那这张表本身又成了单点。

ZK 的方案是把这件事交给"会话"：进程连着 ZK 就有一个会话，节点就存在；会话超时（心跳断了）节点自动消失。于是"这个进程还在吗"变成了"这个节点还在吗"——一个简单的读操作。

/hadoop-ha
├── nn1   (临时节点)   ← 进程活着就存在
└── nn2   (临时节点)   ← 进程活着就存在

8.7 节那个九步自动切换链，全部建立在这一点上。

两个判断技巧

# 看节点是不是临时节点：ephemeralOwner
ls -s /hadoop-ha
# ephemeralOwner = 0x0              → 持久节点
# ephemeralOwner = 0x1a2b3c4d5e...  → 临时节点（这串是会话 ID）

会话不是"TCP 一断就立刻死"——靠心跳维持，超过 sessionTimeout 没心跳才判定过期。这给我们留了重连窗口（网络抖动一下不会立刻切换），也意味着故障发现会有一个超时延迟（秒级）。

8.3 三大角色、五大特性与集群搭建

三个角色

角色能读能写参与投票说明
Leader✅✅✅唯一的写入口，所有写请求都由它处理并广播
Follower✅转发给 Leader✅处理读请求，参与选举和被选举
Observer✅转发给 Leader❌只读扩容，不参与投票，同步数据但不影响选举延迟

Observer 存在的意义：ZK 的读能力可以靠加节点扩展，但投票节点越多，写性能越差（要广播给更多节点并等过半确认）。Observer 只同步数据、不投票，所以能加读能力而不拖慢写。

五个特性

特性人话解释
顺序一致性同一个客户端的写操作，按发出顺序生效（不会乱序）
原子性一次更新要么全成功、要么全失败，没有中间态
单一视图不管连哪台，看到的都是同一份数据
可靠性一旦更新成功，结果会一直保留（不会回滚）
实时性（最终一致）更新后短时间内所有客户端都能读到最新值——不是"立刻"，是"最终"

底层靠 ZAB 协议（ZooKeeper Atomic Broadcast）保证这些特性，可以理解为"简化版的 Paxos"。课程只点到为止，够用。

集群搭建：三个端口别搞混

# zoo.cfg（三台机器内容相同，只有 myid 不同）
tickTime=2000
dataDir=/export/data/zkdata
clientPort=2181

server.1=node1:2888:3888
server.2=node2:2888:3888
server.3=node3:2888:3888
端口用途
2181客户端连接端口（zkCli.sh 连这个）
2888Follower 连 Leader 的数据端口——传写请求和同步数据
3888选举端口——集群选主时互相投票

server.N 里的 N 必须和那台机器的 myid 一致。myid 是手工写在 dataDir/myid 里的一个数字，全局唯一。

server.1/2/3 这三行的作用不只是"告诉别人我在哪"，还告诉每台机器"整个集群一共有几台"。

没有这份清单，一台机器就不知道自己那 1 票算不算过半——选举需要知道总人数才能判断是否过半。

起不来的十条排查

现象原因
报 myid file is missingdataDir 下没有 myid 文件
报 Invalid configuration, only one server specifiedstandalone 模式（zoo.cfg 里没有 server.N 行），或 myid 重复
进程起来了但一直选不出 Leader存活的节点数不过半——3 台只起了 1 台
报 Address already in use2181/2888/3888 被占用
连不上但进程在防火墙没关
dataDir 目录不存在要先手动建

排查入口固定：bin/zkServer.sh status 看模式，日志看 logs 目录下的 zookeeper.out 或 .log。

8.4 两次选举：规则一样，重点不同

ZK 的选举只在两种时刻发生，规则是同一套，但有效比较项不同：

首次选举（冷启动）宕机重选（运行中）
有数据吗无，所有机器 zxid = 0有，各机器数据进度不同
实际比什么只比 myid（zxid 全一样，比了也没意义）zxid 优先，分出胜负就结束
选出谁启动顺序决定的"第 (N+1)/2 台"数据最新的那台
目的从无到有产生一个主防止数据回退

规则就一句

先比 zxid  →  大的赢（事务越新越优先）
zxid 相同  →  再比 myid，大的赢（编号大的优先）

写成元组就是比较 (zxid, myid) 的字典序，取最大者。

zxid 是什么：全局事务 ID，每次写操作 +1，整个集群唯一。所以"谁的数据新"不用比内容，看一眼 zxid 大小就行——这是 ZK 把"数据一致性"和"选举"绑在一起的巧妙之处：选 Leader 本质上是在选"最新的那份数据"。

两个反直觉的结论，面试爱考：

① 三台集群，当选的常常是 2 号，不是 3 号。因为集群是按顺序启动的：1 号启动时只有自己，投自己；2 号启动后，1 号和 2 号互相投票，2 号 myid 大，拿到 2 票 = 过半（3 台的过半是 2），选举就此结束，3 号还没启动。所以是"依次启动 + 过半即止"的必然结果。

② 4 台不比 3 台可靠。4 台的过半是 3，所以只能挂 1 台；3 台的过半是 2，也只能挂 1 台。容错能力一样，成本多一台。这就是集群规模只用奇数的算术原因。

一个技术诚实度提醒：教学版讲的"1 号主动让票给 2 号"是简化模型。真实的 Fast Leader Election 是每轮把票投给"当前已知 (zxid, myid) 最大者"并广播，收到更大的就改投。结论（谁当选）一致，过程机制不同——面试被追问细节时别把简化版当实现讲。

8.5 Watch 与四类典型应用

Watch 的四个性质

性质含义
发布订阅客户端对某节点注册监听，节点变化时收到通知
一次性触发触发一次后就失效，必须重新注册
异步回调通知是异步推过来的，不是同步返回
有序性客户端先看到通知、再看到新数据（不会先读到新值才发现变了）
「一次性触发」是 ZK 最高频的线上 bug 来源。

症状：第一次改配置生效了，第二次不生效。原因就是回调函数里忘了重新注册 watch。

设计成这样是为了避免"数据频繁变化时客户端被通知淹没"，代价就是把重新注册的责任交给了使用者。写 watch 回调时，第一件事就是再 watch 一次。

四类典型应用

应用用的哪个特性怎么做
配置中心持久节点 + Watch配置内容放 znode，所有客户端 watch 它；改了配置，全部收到通知并重读
选主 / Master 选举临时节点所有人抢着创建同一个临时节点，创建成功的那个当主；其余 watch 它，节点消失就去抢
分布式锁临时顺序节点 + Watch每个客户端创建临时顺序节点，序号最小的持有锁；其余只 watch 前一个，前一个释放了就轮到自己
命名服务持久顺序节点用唯一路径当全局 ID（比如 /ids/order/0000001）
注意"选主"和"分布式锁"的区别：都是抢节点，但选主是"只有一个主长期在位"，锁是"轮流持有"。

选主：抢到就一直当主，直到进程挂掉（临时节点消失）。
锁：用完主动释放（删除节点），下一个接上。用顺序节点是为了公平——先来的先拿，而不是所有人一起抢导致惊群。

课程还提了一句很实际的话：在大数据领域，ZK 最主要的真实用途就是 Hadoop HA。配置中心、命名服务这些用得不多（有 Nacos、Consul 等更专门的工具），分布式锁更多用 Redis。所以学 ZK 在这门课里的落点很清楚——为了下一节。

8.6 Hadoop HA：为什么需要三个组件

先回顾问题：NameNode 是单点，它挂了整个集群不可用。而第 02 章讲过，SecondaryNameNode 兜不住——它落后一个 checkpoint 周期，用它恢复会丢最后那一小时的操作。

所以 HA 要解决的是三件事，各对应一个组件：

要解决的问题组件怎么做
要有备胎两个 NameNode
（Active + Standby）		Active 对外服务，Standby 只同步元数据、随时待命
备胎怎么跟上进度JournalNode 集群
（通常 3 台）		Active 把 edits 写到 JN，Standby 从 JN 读 edits 重放，元数据保持同步
谁来判定该切换ZKFC
（每台 NN 上一个）		监控 NN 健康 + 抢 ZK 上的临时节点，抢到的是 Active

为什么用 JournalNode 而不是共享目录

早期方案是"两个 NN 挂同一个 NFS 共享目录，都往里写 edits"。问题很直接：NFS 本身是单点——它挂了两个 NN 一起废，等于把单点从 NN 转移到了 NFS。

QJM（Quorum Journal Manager）的思路是用多个 JournalNode 组成一个小集群：Active 往所有 JN 写，写成功过半即算成功；Standby 从 JN 读。因为要过半，所以 JN 通常配 3 台（容忍挂 1 台）。这本质上是把 ZK 的过半思想用在了日志同步上。

三个组件的关系，一张图说清

        ┌──────── ZK 集群（3 台）────────┐
        │   只存一个临时节点：谁是 Active   │
        └───────┬──────────────┬─────────┘
                │ 抢节点        │ 抢节点
           ┌────┴────┐    ┌────┴────┐
           │ ZKFC-1  │    │ ZKFC-2  │      监控本地 NN 健康
           └────┬────┘    └────┬────┘
           ┌────┴────┐    ┌────┴────┐
           │  NN-1   │    │  NN-2   │      Active / Standby
           │(Active) │    │(Standby)│
           └────┬────┘    └────┬────┘
                │ 写 edits      │ 读 edits 重放
        ┌───────┴───────────────┴───────┐
        │   JournalNode 集群（3 台）      │   过半写成功即算成功
        └───────────────────────────────┘

8.7 自动切换：九步链与 fencing

这是全章最值钱的一段，把 ZK 的三个知识点（临时节点、Watch、过半）一次性用完了。

① 正常态
   nn1 = Active，ZKFC-1 持有 /hadoop-ha/cluster1/ActiveStandbyElectorLock（临时节点）
   nn2 = Standby，ZKFC-2 watch 着这个节点，同时在追 JN 的 edits
        ↓
② 故障发生
   nn1 进程崩溃 / 机器断电 / 网络隔离
        ↓
③ ZK 感知
   nn1 与 ZK 的 session 超时（秒级）
        ↓
④ 临时节点消失
   ZK 自动删除 ActiveStandbyElectorLock（临时节点的本质）
        ↓
⑤ 通知 Standby
   ZK 向 watch 了这个节点的 ZKFC-2 推送 NodeDeleted 事件
        ↓
⑥ 抢锁
   ZKFC-2 立刻创建同一个临时节点（ZK 保证只有一个赢家）
        ↓
⑦ fencing（关键！见下）
   确认旧 Active 真的死了 / 把它彻底隔离掉
        ↓
⑧ 提升
   ZKFC-2 对本地 nn2 调 transitionToActive → nn2 变 Active
        ↓
⑨ 客户端无感
   客户端配的是 ConfiguredFailoverProxyProvider，连 hdfs://cluster1
   它自动去问 ZK 谁是 Active，重连到 nn2 —— 业务代码一行不改

耗时秒级（session 超时 + 一次创建 + fencing）。对比 SNN 方案的"小时级 + 人工"，这就是 HA 的价值。

脑裂：ZK 管不了的那一半

ZK 只保证"选出来的主唯一"——它保证同一时刻只有一个 ZKFC 抢到节点。但它管不了那个已经失联的旧主还在干活。

脑裂场景：旧 Active 没死，只是和 ZK 断了（网络分区）。

此时：旧 Active 以为自己是主，继续接受客户端写；新 Active 也被选出来了，也在接受写。两个 NN 同时写元数据 → 数据损坏。

更糟的是：旧 Active 如果还能连 JN，它会继续往 JN 写 edits，和新主互相覆盖。

所以第 ⑦ 步的 fencing（隔离）不是可选项，是必需项。常见手段有两种：

手段做法说明
sshfenceSSH 到旧 Active 那台机器，直接 kill 掉进程最常用。要求配置免密登录
shellfence执行一个自定义脚本（比如关电源、断网）用于物理隔离或对接 IPMI
fencing 失败 = 不允许切换。

这是个刻意的取舍：宁可服务不可用，也不能让两个主同时写。可用性让位于数据正确性——这条原则在大数据体系里反复出现（HDFS 宁可进安全模式也不乱写、ZK 宁可选不出主也不双主）。

（16 · 08:23–12:21；fencing 配置见 17 · 13:58）

8.8 部署与排错

六个关键配置

<!-- hdfs-site.xml -->
<!-- ① 给集群起个名字，客户端连 hdfs://cluster1 而不是具体机器 -->
<property>
  <name>dfs.nameservices</name><value>cluster1</value>
</property>

<!-- ② 这个集群有哪两个 NN -->
<property>
  <name>dfs.ha.namenodes.cluster1</name><value>nn1,nn2</value>
</property>

<!-- ③④ 两个 NN 各自的 RPC 地址 -->
<property>
  <name>dfs.namenode.rpc-address.cluster1.nn1</name><value>node1:8020</value>
</property>
<property>
  <name>dfs.namenode.rpc-address.cluster1.nn2</name><value>node2:8020</value>
</property>

<!-- ⑤ 共享日志目录（QJM），多个 JN 用分号隔开 -->
<property>
  <name>dfs.namenode.shared.edits.dir</name>
  <value>qjournal://node1:8485;node2:8485;node3:8485/cluster1</value>
</property>

<!-- ⑥ 客户端用哪个代理类自动找 Active -->
<property>
  <name>dfs.client.failover.proxy.provider.cluster1</name>
  <value>org.apache.hadoop.hdfs.server.namenode.ha.ConfiguredFailoverProxyProvider</value>
</property>

<!-- ⑦ 开自动切换（关掉就只能手工 haadmin 切） -->
<property>
  <name>dfs.ha.automatic-failover.enabled</name><value>true</value>
</property>

启动顺序不能乱

ZK 集群  →  JournalNode  →  格式化并启动 NN  →  ZKFC  →  DN / NM
格式化这一步在 HA 模式下最容易错：

format 只能做一次，而且两个 NN 要用同一个 clusterId。做法是：先 format nn1，然后把 nn1 的元数据目录 scp 到 nn2，或者 format nn2 时显式指定 -clusterId 与 nn1 一致。两边各 format 一次会得到两个 clusterId，DataNode 会拒绝加入。

另外要先 hdfs zkfc -formatZK 在 ZK 上建好 HA 的目录结构，否则 ZKFC 起不来。

三个答疑整理成的排错清单

现象原因与解法
两个 NN 都是 StandbyZKFC 没起，或 formatZK 没做。先 jps 看有没有 ZKFC 进程
报 8485 连接不上不是错误——JN 启动后要 2~3 分钟才开始监听端口。等一会再看，别急着改配置
ZKFC 起不来看日志：多半是 ZK 连不上或 ha.zookeeper.quorum 配错
格式化报 NameNode is not formatted没 format，或 format 了另一台
手工切换报错hdfs haadmin -transitionToActive 缺 --forcemanual；手工切换绕过了 ZKFC 和 fencing，只在 ZK 彻底坏掉时救急
Standby 不能写正常——Standby 只读，写请求会报 StandbyException

单独起某个 NameNode：hdfs --daemon start namenode，在对应机器上执行。排错时常用——单独起能立刻看到它自己的报错。

这一章的三条线

① 抽象线：ZK 把"进程活着"抽象成"临时节点存在"，把"变化通知"抽象成"Watch"。有了这两个抽象，分布式协调就变成了对一棵树的读写。

② 一致性线：ZK 靠过半保证自己一致，HDFS 靠 ZK 保证主唯一，JN 靠过半保证日志不丢。同一个"过半"思想用了三次。

③ 取舍线：fencing 失败就不许切换——宁可不可用，不可双写。这条原则贯穿整个大数据体系，值得单独记住。
