03 · Hive 数仓构建

前两章你造的是"存储 + 算力"，但没人会直接用 HDFS 做报表——因为写 MapReduce 太慢。这一章先讲清数据仓库这个领域在干什么（分层、ETL、OLTP 与 OLAP 的分野），再把 Hive 装上、启动、连上去。先懂业务为什么这么分层，后面的建表、分区、优化才有落点；否则你只是背了一堆语法。

内容基准 主体素材：Hadoop 实战课第 10 天（13 个有效视频，另有 1 个"回顾"和 1 个"串讲"已跳过）　·　2026-11 提炼 需留意：3.5 / 3.6 的版本号与路径以课程环境（Hive 3.1.2 + Hadoop 3.3.0 + MySQL）为准，guava 版本冲突是这组版本特有的坑；3.1~3.4 是行业通用方法论，不受版本影响。文中标「补充」的部分课程未展开。

3.1 数据仓库是什么：一句话定住它

先给一句能定住全局的话，它后面所有的性质都是这句的推论：

数据仓库既不生产数据，也不消费数据。

它不产生业务数据（那是 MySQL 这些业务库的事），也不直接给终端用户看（那是报表、App、接口的事）。它站在中间：把散在各处的数据收进来、洗干净、按主题重组、算成指标，再交给下游。

由这一句能推出四个特征（数仓的教科书定义，面试常问）：

特征含义从哪推出来的
面向主题按"用户""订单""商品"这类分析主题组织，不按业务系统的模块组织因为要回答分析问题，不是完成一笔交易
集成多个源系统的数据要统一口径、统一编码、统一单位后才能放在一起因为数据来自多处，不集成就没法比
非易失数据一旦进来基本不改，只追加不修改（改也是整分区重刷）因为要留历史快照做趋势分析
随时间变化每条数据都带时间维度，记录"某时刻的状态"因为分析的本质就是看变化

课程用一个真实场景说明了"为什么必须建数仓"：一家公司有几十个业务系统（寿险、财险、银行、投资），每个系统一套数据库，字段口径还都不一样。老板问"上个月集团总共多少新增客户"，没人能在一小时内答出来——因为要去十几个库捞数据、还要人工对齐口径。这就是数仓存在的理由：把"回答一个问题要几天"变成"几分钟"。

3.2 OLTP 与 OLAP：一条分界线

"Hive 和 MySQL 有什么区别"是面试高频题。标准答法不是比功能，而是先说它们属于两个不同的世界：

OLTP（On-Line Transaction Processing）= 联机事务处理，落到操作就是增删改查。
OLAP（On-Line Analytical Processing）= 联机分析处理，落到操作就是大规模聚合查询。
维度OLTP（MySQL / Oracle）OLAP（Hive / Spark SQL / ClickHouse）
面向面向应用，支撑一笔笔业务面向主题，支撑经营决策
数据当前值（订单此刻的状态）历史快照（过去每一天的状态）
来源自身业务产生，是源头不生产，来自多个外部源
操作增删改查都频繁大量读、极少写，只有导入与分析
量级MB ~ GBGB ~ PB
响应毫秒级，回车即出秒到分钟，慢的按小时算
典型产品MySQL、Oracle、PostgreSQLHive、Spark SQL、ClickHouse、Doris
一句话记法：OLTP 关心"这一笔业务对不对"，OLAP 关心"这一段时间的趋势是什么"。

所以 MySQL 上跑一个千万行的 group by 会卡死，而 Hive 上跑同样的查询是日常——不是 Hive 更"强"，是它放弃了毫秒响应和事务，换来吞吐。

顺带说清 Hive 的定位：它是把 SQL 翻译成 MapReduce（或 Tez/Spark）作业的工具，自己不存数据（数据在 HDFS）、自己不算数据（算力在 YARN）、只存"表长什么样"（元数据在 MySQL）。所以 Hive 天然属于 OLAP 那一侧。

3.3 分层架构：ODS / DWD / DWS / DWT / ADS

数仓最容易被讲成一堆名词的地方就在这。但只要抓住"每一层解决一个问题"，五层一下就顺了。

层全称一句话职责数据形态
ODSOperational Data Store
贴源层		原样落地：业务库什么样就什么样，不洗不改与源表结构一致，按 dt 分区存每日全量/增量
DWDData Warehouse Detail
明细层		清洗 + 规范化：去重、剔脏、统一单位、维度退化一行一条业务事实（一个订单、一次登录）
DWSData Warehouse Summary
汇总层		按维度聚合：把明细按"用户 / 商品 / 天"滚起来一行一个"维度组合 + 指标"，轻聚合
DWTData Warehouse Topic
主题层		拼宽表：把同一主题的多个汇总拼到一行用户主题宽表、商品主题宽表
ADSApplication Data Service
应用层		出指标：直接对接报表、接口、大屏一张表就是一个业务指标集

光看职责还是抽象，走一遍真实需求最清楚。需求：统计每日活跃用户的订单金额。

层表（示例）做了什么
ODSods_order_info、ods_user_login_log从业务库原样同步，按 dt 分区，一个字段都不改
DWDdwd_trade_order_detail、dwd_user_login_detail订单去重、剔除取消单和测试单、金额统一到元；登录日志剔除爬虫与异常 IP
DWSdws_trade_user_order_1d按 user_id + dt 汇总当日下单金额与笔数；标记当日是否活跃
DWTdwt_user_topic_1d把"当日是否活跃"和"当日消费金额"拼到同一行——用户主题宽表
ADSads_dau_order_amount_1d输出三个数：日活用户数、活跃用户订单总额、活跃用户客单价
注意这条链路的"收敛性"：ODS 有几十上百张表，到 DWS 只剩几张，到 ADS 只剩一张。

越往下游，表越少、算得越轻、查得越快。这就是分层的形状——一个漏斗，不是一个仓库。

还有一个常被问的：数据集市（Data Mart）是什么？它是数仓的一个子集，面向某个部门（比如只服务销售部）。区别是数仓面向全公司、集市面向单部门。小公司经常直接跳过数据集市，因为数仓还不够大。

3.4 为什么分层，以及 ETL 与 ELT 的分水岭

分层的五条理由，其实是三条

课程给了五条：结构清晰、血缘追踪、减少重复开发、复杂问题简单化、屏蔽原始数据异常。听着都对，但真正能撑住"必须分层"这个结论的只有三条：

理由具体含义不分层会怎样
减少重复计算DWS 的日汇总被十个报表复用，只算一次十个报表各写一遍 SQL，各扫一遍全量，集群被拖死
隔离变化口径变了只改 DWD 一处，下游不动源表字段改名，几十个下游任务全挂
血缘可追指标异常时沿上一层逐级回溯，几小时定位到源头一个数对不上，从报表一路查到业务库，几天查不出

其余两条（结构清晰、复杂问题简单化）是前三条的副产品。记住"减少重复计算 + 隔离变化"，这两条是分层的经济动机——分层不是为了好看，是为了省算力和省人力。

ETL 与 ELT：差别只在 T 和 L 谁先

三个字母：Extract 抽取、Transform 转换、Load 加载。差别全在顺序。

# ETL：先转换，再加载
数据源  →  [ETL 工具内清洗转换]  →  数仓  →  分析

# ELT：先加载，再转换
数据源  →  数仓（原始数据先落地）  →  [数仓内用 SQL 转换]  →  分析
ETLELT
转换在哪数仓外面（专用工具里）数仓里面（SQL 里）
对工具要求高（Sqoop / Flume / DataX / Kettle）低，但对 SQL / Python 能力要求高
原始数据不进仓，只有干净数据进原样留一份，可回溯可重跑
时代传统行业数仓的主流大数据时代的默认做法
为什么大数据时代 ELT 流行了——这条因果链值得记住：

① ETL 时代存储贵、算力贵，只能在仓外借专用工具"边抽边算"，尽量少落盘；
② HDFS + 廉价磁盘让存储成本大幅下降，"先把原始数据全量存下来"不再奢侈；
③ Hive / Spark 让算力可横向扩展，对海量数据直接跑 SQL 完全可行；
④ 于是转换从"加载前"挪到"加载后"——先存下来再算，原始数据还留了一份，可回溯、可重跑、可换口径重算；
⑤ 结果就是 ELT 成为主流，且天然对应 ODS"原样落地"的定位。

反过来记一句话：ELT 不是"不做转换"，只是把转换推迟到了仓内。很多人以为 ELT 就是"不洗数据"，这是误解——不洗数据的后果是脏数据污染全链路。

3.5 三种部署方式：差在两个地方

课程花了 20 分钟讲这个，因为很多人一开始就理解错了。判断标准只有两条：元数据库在哪、Metastore 服务是否独立——不是"装在哪台机器"。

先把两个概念钉死：

  • 元数据库（Metastore DB）：存"有哪些库、哪些表、表有哪些字段、数据在 HDFS 哪个路径"。默认是 Derby，生产换 MySQL。
  • Metastore 服务：一个 Thrift 服务（默认 9083 端口），客户端通过它读写元数据。它可以跟 Hive 同进程，也可以独立成服务。
模式元数据库Metastore 服务能否多客户端用在哪
内嵌
embedded		Derby（Hive 自带）跟 Hive 同进程不能，同一时刻只允许一个会话自己试玩、跑个 hello world
本地
local		MySQL（独立）跟 Hive 同进程受限于同进程，一般也不并发单机开发、学习过渡
远程
remote		MySQL（独立）独立服务（9083）能，多客户端共享一份元数据生产与课程环境都用这个
内嵌模式的坑：Derby 是单会话独占的。你开了一个 hive 窗口，另开一个就连不上，报 Another instance of Derby may have already booted。这是新手第一次装 Hive 最常见的困惑——不是装错了，是内嵌模式天生如此。

课程直接选了远程模式，理由很实在：只有它支持多客户端，而真实开发就是这样——你用 DataGrip 连、同事用 beeline 连、调度系统用 JDBC 连，读的都是同一份元数据。

3.6 远程模式安装：七步走到能启动

这一段是全章最容易翻车的地方。按顺序做，每步都有验收标准。

① 前置：Hadoop 侧要开用户代理

Hive 启动时会以"提交人"的身份去操作 HDFS，必须允许代理。在 core-site.xml 加三项并重启 Hadoop：

<property>
    <name>hadoop.proxyuser.root.hosts</name>
    <value>*</value>
</property>
<property>
    <name>hadoop.proxyuser.root.groups</name>
    <value>*</value>
</property>

不加会在建表时报 Permission denied: user=hive, access=WRITE——明明你是 root，它却说 hive 没权限，这个报错很迷惑。

② 解压，然后立刻解决 guava 冲突

cd /export/server
tar -zxvf apache-hive-3.1.2-bin.tar.gz
这一步必须做，否则启动就是 NoSuchMethodError，而且报错完全看不出跟 guava 有关。

原因：Hive 3.1.2 自带 guava-19.0.jar，而 Hadoop 3.3.0 用的是 guava-27.0-jre.jar。同一个类两个版本共存，Hive 加载到旧的那个就缺方法。

原则：以 Hadoop 侧版本为准，把 Hadoop 的 guava 拷进 Hive 的 lib，不是反过来。

cd /export/server/apache-hive-3.1.2-bin/lib
rm -rf guava-19.0.jar
cp /export/server/hadoop-3.3.0/share/hadoop/common/lib/guava-27.0-jre.jar ./
ls -l guava*

③ 配 hive-env.sh（模板要改名才生效）

cd /export/server/apache-hive-3.1.2-bin/conf
mv hive-env.sh.template hive-env.sh
vim hive-env.sh        # 末尾追加三行
export HADOOP_HOME=/export/server/hadoop-3.3.0
export HIVE_CONF_DIR=/export/server/apache-hive-3.1.2-bin/conf
export HIVE_AUX_JARS_PATH=/export/server/apache-hive-3.1.2-bin/lib
变量作用
HADOOP_HOME让 Hive 找到 Hadoop，加 classpath、调 HDFS/YARN 客户端
HIVE_CONF_DIR指定 hive-site.xml 等配置所在目录
HIVE_AUX_JARS_PATH附加 jar 目录，第三方 UDF、驱动从这加载

④ 新建 hive-site.xml（包里没有这个文件）

注意是新建，不是改——包里的 conf 目录只有模板和默认文件。

<?xml version="1.0" encoding="UTF-8"?>
<?xml-stylesheet type="text/xsl" href="configuration.xsl"?>
<configuration>

  <!-- ① 元数据库连接串 -->
  <property>
    <name>javax.jdo.option.ConnectionURL</name>
    <value>jdbc:mysql://node1:3306/hive3?createDatabaseIfNotExist=true&amp;useSSL=false&amp;characterEncoding=UTF-8</value>
  </property>

  <!-- ② 驱动类全名，必须和 lib/ 下 jar 版本对应 -->
  <property>
    <name>javax.jdo.option.ConnectionDriverName</name>
    <value>com.mysql.jdbc.Driver</value>
  </property>

  <property>
    <name>javax.jdo.option.ConnectionUserName</name>
    <value>root</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionPassword</name>
    <value>你的密码</value>
  </property>

  <!-- ⑤ 数仓在 HDFS 上的根目录 -->
  <property>
    <name>hive.metastore.warehouse.dir</name>
    <value>/user/hive/warehouse</value>
  </property>

  <!-- ⑥ 远程模式核心：客户端去哪找 Metastore -->
  <property>
    <name>hive.metastore.uris</name>
    <value>thrift://node1:9083</value>
  </property>

  <!-- ⑦⑧ HS2 绑定地址与端口 -->
  <property>
    <name>hive.server2.thrift.bind.host</name>
    <value>node1</value>
  </property>
  <property>
    <name>hive.server2.thrift.port</name>
    <value>10000</value>
  </property>

</configuration>

四个 javax.jdo.option.* 是元数据库"四件套"，缺一个 Metastore 就起不来：

属性常见错误
ConnectionURL库名写错 → 表建到别的库；& 在 XML 里必须写成 &amp;，否则 XML 解析直接失败
ConnectionDriverName5.x 驱动是 com.mysql.jdbc.Driver，8.x 是 com.mysql.cj.jdbc.Driver，写错报 No suitable driver
ConnectionUserName用了只能本机登录的账号，远程连被拒
ConnectionPassword改密码后忘了同步这里

⑤ 放 MySQL 驱动 jar

cp mysql-connector-java-5.1.38.jar /export/server/apache-hive-3.1.2-bin/lib/

驱动版本要和 ② 里的类名对齐：5.1.x 配 com.mysql.jdbc.Driver，8.x 配 com.mysql.cj.jdbc.Driver。混搭是这个环节最隐蔽的错——jar 放了、类名也写了，就是不匹配。

⑥ MySQL 侧：建库 + 允许远程 + 8.x 认证插件

-- 建元数据库（字符集必须 utf8，否则中文注释乱码）
CREATE DATABASE hive3 DEFAULT CHARACTER SET utf8;

-- 允许 root 从任意主机连（学习环境；生产要限 IP）
USE mysql;
UPDATE user SET host='%' WHERE user='root';
FLUSH PRIVILEGES;

-- MySQL 8.x 特有：驱动不认 caching_sha2_password
ALTER USER 'root'@'%' IDENTIFIED WITH mysql_native_password BY '你的密码';
MySQL 8.x 的认证插件是新版最大的坑。8.0 默认用 caching_sha2_password，而老版 JDBC 驱动只认 mysql_native_password，表现是密码明明对，却报 Access denied。要么改认证插件（上面这条），要么换 8.x 驱动并改类名。

⑦ 初始化元数据库

schematool -dbType mysql -initSchema

这一步做的是在 MySQL 的 hive3 库里建 50 多张元数据表（DBS、TBLS、COLUMNS_V2……）。验收标准：末尾输出 Initialization script completed + schemaTool completed。

如果第一次执行失败，重试前要先 DROP DATABASE hive3 重建——因为中途失败会留下半套表，再 init 会撞"表已存在"。

⑧ 建 HDFS 目录并授权

hdfs dfs -mkdir -p /user/hive/warehouse
hdfs dfs -mkdir -p /tmp/hive
hdfs dfs -chmod -R 777 /user/hive/warehouse
hdfs dfs -chmod -R 777 /tmp/hive

/tmp/hive 是 Hive 的临时目录（存中间结果、会话文件），不放权限会报 Failed to create directory。

（08 · 全篇；MySQL 8.x 认证插件与 HDFS 授权为补充）

3.7 启动顺序与四个客户端

顺序不能乱

MySQL  →  Hadoop（HDFS + YARN）  →  Metastore（9083）  →  HiveServer2（10000）  →  客户端

每一环都是下一环的前提：Hadoop 没起，Metastore 起来也读不到 HDFS；Metastore 没起，HS2 起来也读不到表结构。

第一次一定前台启动，别急着 nohup。配置手抖改错是常态，前台能看到完整报错：
cd /export/server/apache-hive-3.1.2-bin
bin/hive --service metastore       # 看到 Starting Hive Metastore Server 且长时间无报错 = 配置对
# Ctrl+C 停掉，再后台起

确认无误后后台起两条：

nohup /export/server/apache-hive-3.1.2-bin/bin/hive --service metastore \
  > /export/server/apache-hive-3.1.2-bin/metastore.log 2>&1 &

nohup /export/server/apache-hive-3.1.2-bin/bin/hive --service hiveserver2 \
  > /export/server/apache-hive-3.1.2-bin/hiveserver2.log 2>&1 &

三个验收信号

# ① 进程：应该有两个 RunJar
jps

# ② 端口：10000 被监听才算 HS2 好了
netstat -nltp | grep 10000

# ③ 日志：出错看这里
tail -100 hiveserver2.log
HS2 首次启动要 3~5 分钟。这段时间客户端连必失败，报 Connection refused。"连不上"的绝大多数情况是端口还没 LISTEN，不是配置错了。日志出现 Starting HiveServer2 才算起来，出现 HiveServer2 started 更稳。

四个客户端，四条路径

客户端命令连谁状态
老客户端bin/hive直连 Metastore，绕过 HS2已不推荐，可本地调试
新客户端bin/beeline经 JDBC 连 HiveServer2官方主推，支持并发
图形化DataGrip / DBeaverJDBC 连 HS2日常开发最顺手
程序JDBC / PythonJDBC 连 HS2调度系统用这个

beeline 是两步：先进交互界面，再 connect。

bin/beeline
# 提示符变 beeline> 之后：
!connect jdbc:hive2://node1:10000

3.8 用脚本管住两个 RunJar

为什么必须写脚本

痛点具体表现
命令太长每次手敲 nohup /export/server/.../bin/hive --service metastore
必须后台前台跑法终端被占死，只能再开窗口
停不掉kill metastore、kill hiveserver2 完全无效——进程名不叫这个
记 PID 麻烦两个进程号每次都不一样
关键发现：这两个服务在进程表里统一叫 RunJar。

因为 hive 脚本本质是 java -cp ... org.apache.hadoop.util.RunJar。所以按名字 kill 杀不掉，只能先取 PID 再 kill -9。

取 PID 用 jps | grep RunJar | awk '{print $1}'——jps 输出两列"PID 名称"，取第一列。用 ps -ef 的话第一列是用户名、第二列才是 PID，别混。

完整脚本

#!/bin/bash

read -p "请输入您要执行的动作(start|stop): " action

case $action in
  start|S)
    start-all.sh
    nohup /export/server/apache-hive-3.1.2-bin/bin/hive --service metastore \
      > /export/server/apache-hive-3.1.2-bin/metastore.log 2>&1 &
    nohup /export/server/apache-hive-3.1.2-bin/bin/hive --service hiveserver2 \
      > /export/server/apache-hive-3.1.2-bin/hiveserver2.log 2>&1 &
    ;;
  stop|T)
    for i in $(jps | grep RunJar | awk '{print $1}')
    do
      kill -9 $i
    done
    stop-all.sh
    ;;
  *)
    echo "您的输入有误，请重新输入"
    ;;
esac
chmod +x hive-manager.sh
./hive-manager.sh
# 输入 S → 起 Hadoop + Metastore + HS2；输入 T → 全停

这一章的三层收获

① 概念层：数仓不生产也不消费数据；OLTP 与 OLAP 的分野决定了技术选型；五层架构是一个"表越来越少"的漏斗。

② 方法层：分层的经济动机只有两条——减少重复计算、隔离变化；ELT 流行是因为存储和算力变便宜了，不是因为它"更先进"。

③ 操作层：guava 对齐、驱动类名与 jar 版本对齐、MySQL 8.x 认证插件、HS2 启动慢——四个坑全是"配置看着对但就是起不来"的类型，排查时按"版本对齐"这个思路走，比逐个试快得多。
