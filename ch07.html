07 · MapReduce 与 YARN

前四章你一直在写 SQL，Hive 把它翻译成 MapReduce 交上去。这一章拆开那个盒子：一个作业到底怎么被切成 Map、怎么排序、怎么汇总，以及它跑在什么上面（YARN 的资源调度）。不学这一章，第 09 章的 Hive 优化就只能靠背结论——因为你不知道为什么调 reduce 数、不知道 shuffle 贵在哪、不知道作业为什么排队。

内容基准 主体素材：Hadoop 实战课第 14 天（15 个有效视频，另有 1 个"回顾"和 1 个"串讲"已跳过）　·　2026-11 提炼 需留意：7.8 的默认调度器与 Hadoop 版本有关（Apache 3.x 默认 Capacity、CDH 默认 Fair），以你集群 yarn-site.xml 实际配置为准；7.1~7.7 是机制，各版本一致。

7.1 分布式计算：把程序搬过去，而不是把数据搬过来

先看一个最朴素的问题：一台机器算不完，用多台怎么算？

最直觉的做法是"把数据从各台机器收集到一台，集中算"。这个方案在数据量小时可行，但在这里彻底不成立——因为要搬的是 TB 级数据，而程序只有几 KB。

核心设计：计算找数据，不是数据找计算。

把程序（jar 包）分发到数据所在的机器上，每台机器就地算自己那块，最后汇总结果。

代价对比：搬 1 TB 数据 vs 搬 10 MB 程序。这个选择决定了整个大数据体系的技术路线——也解释了为什么 HDFS 要把块分散在多个节点、为什么机架感知要"就近读"、为什么数据倾斜的代价那么大（一台机器上数据太多，程序搬过去也吃不下）。

两种组织方式：分散汇总 vs 中心调度

分散汇总中心调度
怎么组织各节点自己算，算完把结果报给一个汇总方有一个中心节点统一分配任务、监控进度、处理失败
优点结构简单可控、可容错、可观测
缺点失败无人重试、进度看不见中心节点是瓶颈（所以要做 HA）
Hadoop—选这个：YARN 是中心调度，MR 的 AM 也是中心调度

课程还提到一个很实际的信号：单机跑大数据脚本会报 return code 2，意思是资源不足（内存/CPU 撑不住），不是语法错。看到这个错就该考虑上集群了。

7.2 WordCount：一个案例看穿整个模型

所有 MR 教程都从词频统计开始，因为它足够小，又能完整暴露模型的所有环节。

# 输入（两行）
hadoop flink
hadoop spark

# 期望输出
flink   1
hadoop  2
spark   1

关键在于中间发生了什么：

Map 阶段输出（不是最终结果！）：
<hadoop,1>  <flink,1>
<hadoop,1>  <spark,1>

Shuffle 之后，Reduce 收到的：
<flink,  [1]>
<hadoop, [1,1]>      ← value 变成了列表
<spark,  [1]>

Reduce 输出：
<flink,1>  <hadoop,2>  <spark,1>
这里有一个必须理解的分水岭：Map 输出的是 <词, 1>，Reduce 收到的是 <词, [1,1,1]>。

很多人以为 Map 会直接输出 <hadoop, 2>——这不可能。因为每个 Map 只看得见自己那一片数据，它压根不知道全局有几个 hadoop。

所以 Map 只能做"拆词 + 打标签 1"，真正的累加必须等到 Shuffle 把同一个 key 的所有 value 汇集到一个 Reduce 之后。这一步也是分布式聚合的本质：先局部标记，再全局汇总。

课程里用计数器观察了数据量的变化，这组数字很能说明问题：10 行进 → Map 输出 20 条（一行两个词）→ Combiner 后 5 条 → 最终输出 5 条。中间那个 20→5 就是规约（Combiner）干的活。

7.3 天龙八步（上）：切片、map、分区

课程把整个流程拆成八步，叫"天龙八步"。面试时说"大概分八步"就行，别说"天龙八部"——对方听不懂。

① 读取源文件 + 逻辑切片

InputFormat 按 128 MB 切片，一片对应一个 MapTask。所以"Map 数由文件大小决定"这句话的来源就在这里。

切片时产生的第一条记录是 <K1, V1>：

是什么类型
K1该行在文件中的起始字节偏移量LongWritable
V1整行文本内容Text
"逻辑切片"和"物理切块"是两件不同的事——这是本节最值得记住的区分：
HDFS 切块（Block）MR 切片（InputSplit）
真伪物理切，300 MB 真的变成 3 个块逻辑切，文件一点没动，只是"读的时候到 128 MB 就停"
容差严格 128 MB允许略超，不超过 128 MB × 1.1

那 1.1 倍是干嘛的？如果第 128 MB 正好落在 Hadoop 这个词中间，硬切就把词劈成两半了。所以允许读到 1.1 倍以内，把这一行完整读完再停。这是"按行处理"这个语义的必然要求。

② map()：拆词打标签

K1=0  V1="hadoop flink"
      ↓ map()
<hadoop,1>  <flink,1>      ← K2, V2

注意记录数变了：10 行进、20 条出（因为一行有两个词）。Map 的本质是"拆 + 打标签"——把"一行文本"这种没法聚合的单位，转成"可聚合的键值对"。

③ 分区 Partitioner：决定去哪个 Reduce

默认： (key.hashCode() & Integer.MAX_VALUE) % 分区数
分区是"同一个 key 必须进同一个 Reduce" 的唯一保证。

不分区的后果很具体：hadoop 的记录散在两个 Reduce 里，一个算 3、一个算 2，各输出一行 hadoop 3 和 hadoop 2，结果就是错的。

三条铁律：分区数 = ReduceTask 数 = 最终输出文件数；默认分区数是 1（所以默认只有一个 part-r-00000）；想按月份分文件输出，就按月份分区。

另外注意：分区只是给记录打个标签，不是此刻真的把数据搬走。真正的搬发生在后面的溢写和拉取。

（04 · 00:00–17:29；07 · 03:49 补充）

7.4 天龙八步（下）：排序、规约、分组、reduce、输出

④ 排序 Sort：为了"相邻即同 key"

分区内按 key 字典序排，key 相同则按 value 排。三个理由：

  • Reduce 端靠"相邻即同 key"来分组——不排序就得反复跳跃查找；
  • 合并时相同 key 挨在一起，顺序扫一遍就完事；
  • 副产品：最终输出天然有序，所以 part-r-00000 里是字典序。

⑤ 规约 Combiner：Map 端的局部 reduce

在 Map 端先跑一次"小 reduce"，把相同 key 先加起来。目的是少搬数据——减少溢写量、减少网络传输、减轻 Reduce 压力。实测 20 条变成 5 条。

三条注意事项，第一条最容易出事：

① 只适用于满足结合律 / 交换律的操作。求和、求最大最小可以；求平均值不行——avg(avg(1,2), 3) ≠ avg(1,2,3)，前者是 2，后者是 2，但换成 avg(avg(1,2), 100) 就差了十万八千里。

② Combiner 的执行次数不确定（0 次到多次都可能），所以逻辑必须幂等。

③ 它不是必选项——不写就用默认的，或者干脆不规约直接进下一步。

⑥ 分组 GroupingComparator：value 变成列表

★★★★★ 分组不是合并。这是全章最容易错的概念。 
分组前：<hadoop,1> <hadoop,1> <hadoop,1>
分组后：<hadoop, [1,1,1]>      ← 只换了形状，没做任何加法
reduce() 里才真正累加 → 3

为什么要分组：reduce() 方法一次调用处理一个 key 的全部 value，所以必须先把它们攒成一个迭代器。

为什么这一步不能省：如果你以为 Map 直接输出 <hadoop, 6>，那说明还没理解分布式——每个 Map 只看得见自己那一片，它不可能知道全局有几个。

⑦ reduce()：第一次"全局汇总"

遍历 value 列表累加，输出 <K3, V3>。这一步的意义在于：只有到了这里，一个 key 的全部 value 才第一次凑齐，才谈得上"全局汇总"。

⑧ 输出 OutputFormat：落回 HDFS

写到 /output/part-r-00000（一个 reduce 一个文件）加一个 _SUCCESS 标记文件。

为什么一个 reduce 一个文件：因为各 reduce 之间互不知道对方写了什么，没法往同一个文件里追加。这也是为什么调 reduce 数会直接改变输出文件数——第 09 章讲小文件治理时会用到这一条。

八步速记表

#步骤输入 → 输出一句话理由
①读取 + 切片文件 → InputSplit / K1,V1切几片就有几个 Map
②map()K1,V1 → K2,V2拆词打标签 <词,1>
③分区KV → KV + 分区号同 key 必须同 reduce
④排序乱序 → 区内有序分组靠"相邻"
⑤规约多条 → 少条少搬一点是一点
⑥分组KV → K + 列表value 变 Iterable
⑦reduce()列表 → K3,V3全局汇总
⑧输出KV → part-r-xxxxx落 HDFS

（04 · 17:29–30:55；08 全篇）

7.5 Shuffle：八步里真正贵的部分

上面 ③ 到 ⑥ 这四步合起来叫 Shuffle（洗牌）。它是 MR 里唯一需要跨节点搬数据的地方，也是最慢、最容易出问题的地方——第 09 章的所有优化，一半以上都在减少 Shuffle。

Map 端：写内存 → 溢写 → 合并

map 输出 → 写入【环形缓冲区】（默认 100 MB）
              ↓ 到 80% 就触发
           【溢写 spill】到磁盘，同时按分区+key 排序
              ↓ 多次溢写
           【合并 merge】成一个大文件（仍然分区有序）
环节关键点
环形缓冲区默认 100 MB，到 80% 触发溢写（留 20% 是为了溢写期间还能继续写入，不阻塞）
溢写溢写前会做分区 + 排序，所以每个溢写文件内部都是"按分区归堆、区内按 key 有序"
合并多个溢写文件归并成一个，归并不改变有序性

Reduce 端：主动拉取

一个容易想反的点：Reduce 是主动去拉（pull），不是被动接收（push）。

Reduce 启动后会向所有 Map 节点发请求，把属于自己分区的数据拉过来，然后归并排序、交给分组。这也是为什么"Reduce 卡在 33% 很久"很常见——那个阶段正在拉数据。

Shuffle 五段，一句话说完

面试问"讲讲 Shuffle"，答这五个词就够：collect（写环形缓冲区）→ spill（溢写磁盘）→ merge（Map 端合并）→ copy（Reduce 拉取）→ sort（Reduce 端归并排序）。

7.6 YARN：三大角色与容器

MR 只是"怎么算"，YARN 管的是"在哪算、给多少资源算"。

角色数量职责挂了会怎样
ResourceManager（RM）全局 1 个（可 HA）整个集群的资源总控：接收作业、分配 Container、调度队列整个集群不能提交新作业（所以生产必须 HA）
NodeManager（NM）每台 1 个单机代理：启动/监控 Container、向 RM 汇报本机资源这台机器上的任务全部失败，AM 会去别处重跑
ApplicationMaster（AM）每个作业 1 个这个作业的"项目经理"：申请资源、派任务、监控进度、处理失败这个作业失败，RM 会重启 AM
面试常问"YARN 有几个角色"，标准答法是"物理 2 个、逻辑 3 个"。

物理部署上只有 RM 和 NM 两种进程（jps 里能看到的就这两个）。AM 是每个作业临时起一个，跑完就退出，所以它不算"常驻服务"。

另外别把 AM 和 RM 内部的 ApplicationManager 搞混——后者是 RM 内部的一个组件，负责管理所有 AM，不是 AM 本身。

Container：资源的抽象单位

Container 就是"一块被预占的资源"，比如 1 个 vcore + 1 GB 内存。任务真正跑在 Container 里，且突破不了这个上限（超内存会被 kill）。

所以资源流转是：RM 决定分配 → NM 负责启动 → 任务在 Container 里跑 → 结束后 Container 释放。

7.7 任务提交流程：七步链与通信方向

步动作谁 → 谁
①客户端执行 hadoop jar ...，作业提交客户端 → RM（8032）
②RM 找一个空闲 NM，在那里创建第一个 Container，并在其中启动 AMRM → 某个 NM
③AM 启动后向 RM 注册自己并建立心跳AM → RM
④AM 按作业需求申请资源（单位是 Container）AM → RM
⑤RM 返回有资源的 NM 列表；AM 通知这些 NM 创建容器并启动 taskRM → AM，AM → NM
⑥task 启动后反向注册回 AM 并保持心跳、汇报进度；失败则重建容器重跑Task → AM
⑦作业结束，AM 向 RM 注销，RM 回收所有 ContainerAM → RM
比背步骤更有用的是记住"通信方向"的规律：

① 只有客户端会主动找 RM，提交完就退场，全程不再参与。
② AM 是唯一同时跟 RM 和 NM 都说话的角色：向上找 RM 要资源，向下找 NM 起容器。
③ task 只跟 AM 说话，从不直接找 RM 或 NM——这就是"为什么 task 挂了是 AM 去重启，而不是 RM 管"。

记住这三条，七步自然能推出来，不用死背。

这段能直接复用到 Spark：Spark on YARN 的流程完全一样，唯一区别是 Container 里跑的不再是 MapReduce 程序而是 Spark 程序。背一次，面试问 Spark 也能用。

7.8 三种调度器与日志查看

公司里很多人共用一个集群，作业一个个往同一个 YARN 上提交。谁先执行、谁后执行，得有规则——这就是调度器。

FIFOCapacity（容量）Fair（公平）
核心思想单队列排队，前面跑完才轮到后面集群切成多个队列，每队列有保底容量，队内仍 FIFO动态在所有运行中的作业间平衡
资源分配队头作业独占全部可用资源按队列配比（如 prod 40% / dev 60%）1 个作业拿 100%，2 个各 50%，3 个各 33%
优点简单，大作业能拿满资源多团队互不干扰，整体利用率高每个任务都有资源，不会有大量任务干等
缺点大作业会饿死小作业大作业拿不到全集群；队列内繁忙时仍排队任务一多每人资源很薄，执行时间被拉长
谁默认用很少单独用Apache 开源版默认CDH 等商用版默认

看你的集群是哪个：查 yarn-site.xml 里的 yarn.resourcemanager.scheduler.class，不配就走官方默认（Apache 3.x 是 Capacity）。

容量调度器的两个容量

配置含义不设会怎样
capacity保底容量：这个队列至少能拿到这么多必须设
maximum-capacity上限容量（弹性天花板）：空闲时可以抢到这么多不设上限，队列隔离形同虚设——一个队列可以把整个集群吃满

典型配置：root 下拆两个队列，prod 拿 40%、dev 拿 60%；dev 的 maximum-capacity 设 75%，意思是"平时保底 60%，集群空闲时最多能涨到 75%"。

命令行看日志

# 列出所有作业（含运行中和已结束的）
yarn application -list

# 按状态过滤
yarn application -list -appStates ALL

# 查某个作业的完整日志
yarn logs -applicationId application_1234567890_0001
前提：日志聚集必须开着。

如果 yarn.log-aggregation-enable 是 false，日志只留在跑任务的那台机器的本地目录里，作业结束后机器一换、或者容器一销毁，日志就找不到了，历史服务器上也点不开。

这就是第 03 章 3.6 里那三项日志聚集配置要一起开的原因——不开，事后排障就没有依据。

这一章的三条线

① 计算线：计算找数据（不是数据找计算）；切片决定 Map 数、分区决定 Reduce 数、Reduce 数决定输出文件数。

② 数据形态线：K1,V1（偏移量+整行）→ K2,V2（词+1）→ K2,Iterable（词+列表）→ K3,V3（词+总数）。四次形态变化，每一次都在回答"这一步能做什么、不能做什么"。

③ 资源线：RM 分资源、NM 起容器、AM 管作业、task 只向 AM 汇报。调度器决定排队规则，容量调度器的"保底 vs 上限"决定队列隔离是否真的有效。
