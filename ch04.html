04 · Hive 基础知识

这一章教的是"怎么在 Hive 里定义数据"。看起来都是语法，但真正决定成败的是三个设计决定：数据怎么解析（SerDe）、这张表归谁管（内部还是外部）、数据怎么分目录（分区/分桶）。三者选错，后面的查询再怎么写都快不起来，甚至查不到数。这一章也是全站篇幅最长的一章，因为它是后面所有 SQL 的地基。

内容基准 主体素材：Hadoop 实战课第 11 天（30 个有效视频，另有 1 个"串讲"已跳过）　·　2026-11 提炼 需留意：4.2 的乱码修复依赖 MySQL 版本（8.x 的字符集默认值已变，坑没那么容易踩到，但原理不变）；4.9 的分桶参数在 Hive 3 里默认值有调整，以 SET 实际查看为准。其余章节是机制，不受版本影响。

4.1 心智模型：库是目录，表是目录加文件

学 Hive 最省力的第一步，是先把脑子里"表 = 数据库里的一块存储"这个印象换掉。Hive 的真实结构是这样的：

HDFS
└── /user/hive/warehouse/          ← 数仓根目录（hive.metastore.warehouse.dir）
    ├── db_itcast.db/              ← 一个库 = 一个 .db 结尾的目录
    │   ├── t_students/            ← 一张表 = 一个子目录
    │   │   └── students.txt       ← 真实数据就是普通文本文件
    │   └── t_order/
    │       ├── dt=2026-01-01/     ← 一个分区 = 一个子目录
    │       │   └── 000000_0
    │       └── dt=2026-01-02/
    └── db_hive3.db/
这张图能解释后面几乎所有困惑：

· 为什么建库建表瞬间完成？——因为只是建目录、写元数据，没有搬任何数据。
· 为什么改表名很快？——改的是 MySQL 里的一行记录。
· 为什么分区表能"跳过"大部分数据？——因为分区就是目录，不查的目录压根不打开。
· 为什么 DROP 外部表不丢数据？——因为元数据在 MySQL、数据在 HDFS，两套系统。

元数据（有哪些库、哪些表、字段叫什么、数据在哪）全部存在 MySQL 里，HDFS 上只有数据文件。这两套东西的一致性，就是后面所有"查不到数据"问题的根源。

（01 · 06:30–09:15；03 全篇）

4.2 数据库 DDL 与那个只能提前防的乱码坑

库的五组操作

-- 建（最小）
CREATE DATABASE db_itcast;

-- 建（生产写法：幂等 + 备注 + 自定义属性）
CREATE DATABASE IF NOT EXISTS db_hive3
COMMENT 'hive3 数据库'
LOCATION 'hdfs://node1:8020/user/hive/warehouse/db_hive3.db'
WITH DBPROPERTIES ('createBy' = 'itcast');

-- 查
SHOW DATABASES;                    -- 列出所有库
SHOW DATABASES LIKE 'db_*';        -- 支持通配
DESCRIBE DATABASE EXTENDED db_hive3;  -- 带 DBPROPERTIES

-- 切
USE db_itcast;
SELECT current_database();          -- 确认当前在哪个库

-- 改
ALTER DATABASE db_itcast SET DBPROPERTIES ('dept'='bigdata');

-- 删（CASCADE 连表一起删，RESTRICT 是默认：有表就拒删）
DROP DATABASE IF EXISTS db_itcast CASCADE;

两个容易忽略的点：

  • LOCATION 指向的目录不需要预先建，Hive 会自动创建。
  • DESCRIBE DATABASE 输出里的 Location 那一行是排障关键——它告诉你这个库到底挂在 HDFS 哪个路径，查"数据在哪"第一个看它。

中文 COMMENT 变问号：根因不在 Hive

现象：建库建表都不报错，只有备注里的中文变成 ???：

CREATE DATABASE db_hive3 COMMENT 'hive3 数据库';
DESCRIBE DATABASE EXTENDED db_hive3;
-- 备注显示：hive3 ???
根因：元数据存在 MySQL，而元数据库的字符集是 latin1。

latin1 是单字节编码，只有 255 个码位，根本表达不了汉字。MySQL 收到"数据库"三个字时无处安放，直接替换成 ? 再存进去。

所以这是"写入时就丢了"，不是"显示时才坏"。这也意味着——已经变成 ? 的数据，修好字符集也救不回来，早就是问号了，必须重新执行 COMMENT。

为什么改 hive-site.xml 没用：那里配的是 JDBC 连接参数，管的是"传输过程用什么编码"。但列定义、表定义的字符集在建表那一刻就定死在 MySQL 里了，连接参数管不着。

怎么查

mysql -uroot -p

-- 看元数据库的建表语句，重点看末尾的 DEFAULT CHARSET
SHOW CREATE TABLE hive3.DBS\G
-- ) ENGINE=InnoDB DEFAULT CHARSET=latin1   ← 元凶

-- 直接看数据，确认是存进去就坏了
SELECT DB_ID, NAME, `DESC` FROM hive3.DBS;

三张关键表：DBS（库）、TBLS（表）、COLUMNS_V2（字段）。COMMENT 乱码看这三张。

怎么修：三步，顺序不能乱

① 改 MySQL 服务端默认字符集（/etc/my.cnf）

[mysqld]
character-set-server=utf8
collation-server=utf8_general_ci

[client]
default-character-set=utf8

[mysql]
default-character-set=utf8
systemctl restart mysqld

② 把已存在的元数据表转成 utf8——这一步不能省。改 my.cnf 只影响以后新建的表，已有的 latin1 表不会自己变：

ALTER DATABASE hive3 CHARACTER SET utf8;

ALTER TABLE hive3.DBS        CONVERT TO CHARACTER SET utf8;
ALTER TABLE hive3.TBLS       CONVERT TO CHARACTER SET utf8;
ALTER TABLE hive3.COLUMNS_V2 CONVERT TO CHARACTER SET utf8;

元数据库有 70 多张表，手写不现实。批量生成再执行：

SELECT CONCAT('ALTER TABLE hive3.', table_name,
              ' CONVERT TO CHARACTER SET utf8;')
FROM information_schema.tables
WHERE table_schema = 'hive3';

③ 重建那些带中文 COMMENT 的库和表，因为旧值已经是问号了。

更省事的做法：一开始就别踩。建元数据库时直接写 CREATE DATABASE hive3 DEFAULT CHARACTER SET utf8;——这一句能省掉后面半小时。上一章 3.6 里那条建库语句就是为这个。

（01、02 两集；批量转换脚本为补充）

4.3 建表语法与数据类型

一条建表语句的五个部件

CREATE [EXTERNAL] TABLE [IF NOT EXISTS] db.tb (
    id    INT     COMMENT '编号',       -- ① 字段定义
    name  STRING  COMMENT '姓名'
)
COMMENT '学生表'                          -- ② 表备注
PARTITIONED BY (dt STRING)               -- ③ 分区（可选）
ROW FORMAT DELIMITED                    -- ④ 怎么解析一行
    FIELDS TERMINATED BY ','
STORED AS TEXTFILE                        -- ⑤ 存成什么格式
LOCATION '/stu';                          -- ⑥ 数据在哪
部件作用不写会怎样
① 字段列名 + 类型 + 备注必须有
② COMMENT表和字段的说明，存在 MySQL不写就是空，团队协作时是灾难
③ PARTITIONED BY按目录切分数据全表一个目录，查询扫全量
④ ROW FORMAT配 SerDe，决定怎么切字段默认用 \001，见 4.5
⑤ STORED AS文件格式（TEXTFILE / ORC / PARQUET）默认 TEXTFILE，纯文本
⑥ LOCATION数据目录默认 /user/hive/warehouse/db.db/tb/

原生数据类型

类型对应 Java说明
TINYINT / SMALLINT / INT / BIGINTbyte / short / int / long整数四兄弟，按范围选
FLOAT / DOUBLEfloat / double浮点，金额别用
DECIMAL(p,s)BigDecimal金额用这个，p 总位数、s 小数位
STRINGString万能类型，实际用得最多
VARCHAR(n) / CHAR(n)String有长度限制，很少用
BOOLEANbooleantrue / false
DATE / TIMESTAMPDate / Timestamp日期与时间戳
BINARYbyte[]二进制，少用
实战经验：90% 的字段用 STRING 就对了。

原因很实在——源数据从业务库抽过来时经常有脏值（数字列里混着空串、NULL 字符串、-）。定义成 INT 会让整个文件解析失败或该字段全变 NULL；定义成 STRING 先接住，要用的时候再 CAST。而 STRING 是所有类型的"最宽"端，任何类型都能自动转过去。

类型名大小写不敏感——INT、int、Int 都行，Hive 会统一成大写显示。

复杂数据类型

类型声明访问语法对应 JSON
ARRAYARRAY<STRING>arr[0]（下标从 0 开始）["a","b"]
MAPMAP<STRING,INT>m['k']{"k":1}
STRUCTSTRUCT<name:STRING,age:INT>s.name（点号）{"name":"x"}

三种类型的访问语法不能混：数组用方括号下标、map 用方括号加 key、struct 用点号。写错不会报错，只会返回 NULL——这是排查起来最费劲的一类问题。

隐式转换：一个"能成立所以测不出来"的陷阱

隐式转换显式转换
谁触发Hive 自动你写 CAST
方向窄 → 宽（安全方向）任意方向
失败时静默变 NULL返回 NULL

三条规律够用：数值链单向递增（TINYINT → SMALLINT → INT → BIGINT → FLOAT → DOUBLE，顺向可以逆向不行）；数值 → 字符串永远可以；字符串 → 数值需要显式 CAST。

'1' = 1 在 Hive 里通常返回 true——这正是它危险的地方。

规则：比较运算遇到 STRING 与数值，Hive 把字符串转成 DOUBLE 再比。于是：

SELECT '1'    = 1;   -- true
SELECT '01'   = 1;   -- true   前导零被吃掉
SELECT ' 1'   = 1;   -- true   前导空格被吃掉
SELECT '1'    = '01';-- false  两个都是字符串，按字典序比
SELECT '1abc' = 1;   -- NULL   转换失败

真正的生产事故是第三种情况：某天数据里混进 '1abc'，转换失败返回 NULL，而这个 NULL 在 WHERE 里等于"不成立"，那一行被静默丢掉，不报错、不告警。你的统计数少了几个订单，没人知道为什么。

同类事故还有：JOIN 两侧类型不一致（一边 INT 一边 STRING）→ 部分 key 匹配不上，结果偏少。所以建表时就把类型定对，比事后排查便宜得多。

（04~08 五集；DECIMAL 的实战建议为补充）

4.4 SerDe：Hive 的表是"假的"

先把最容易搞混的一点钉死：HDFS 里没有"表"，也没有"行"和"列"。那里只有一堆文本文件，文件里是一行行字符，每个字符都是字节。1,孙悟空,53 在 HDFS 眼里是十几个字节，它不知道第一个逗号前叫 id。

Hive 要让这堆字节变可用，中间必须有一层翻译官，就是 SerDe = Serializer + Deserializer：

读：HDFS 文件
      ↓ InputFormat  决定"怎么把文件切成一条条记录"
    key-value（key 是行偏移量，value 是这一行内容）
      ↓ Deserializer 决定"这一行怎么切成字段"
    Java 对象 → 表中的一行

写：反过来，Serializer 把 row 转成字节，OutputFormat 写成文件
一句话记住：读文件是反序列化，写文件是序列化。

由此得到一个很重要的推论：SELECT * FROM t 时 Hive 并不是"从表里取数据"——表里根本没有数据。它是现读 HDFS 文件、现切、现组装成行。所以文件一变，查询结果立刻变，不需要任何同步动作。

那么 ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' 是什么？它不是"一个叫分隔符的独立功能"，它就是 SerDe 的配置项——告诉 Hive 用哪个 Deserializer（这里是 LazySimpleSerDe）、按什么规则切。

（09 · 全篇）

4.5 分隔符：为什么"只有第一列有值"

四个子句，覆盖 95% 的场景

ROW FORMAT DELIMITED
  FIELDS TERMINATED BY ','            -- 列与列之间
  COLLECTION ITEMS TERMINATED BY '-'  -- 集合内元素之间
  MAP KEYS TERMINATED BY ':'        -- map 的 key 与 value 之间
  LINES TERMINATED BY '\n'            -- 行与行之间
COLLECTION ITEMS 和 MAP KEYS 最容易被搞混：

COLLECTION ITEMS 管两件事——array 里元素之间、以及 map 里多个键值对之间。
MAP KEYS 只管一件事——map 里 key 和 value 之间。

举个具体例子：数据是 张三,100-数学:90-语文:85，字段是 name STRING, scores MAP<STRING,INT>。这里 - 分隔两个键值对（用 COLLECTION ITEMS），: 分隔 key 和 value（用 MAP KEYS）。两个写反就切错列，结果里全是 NULL 或串行。

默认分隔符是 \001，不是逗号

这是最容易踩的一个坑：不写 ROW FORMAT 时，Hive 用的默认字段分隔符是 \001（ASCII 的 SOH，Ctrl+A），既不是逗号也不是制表符。

于是产生一个"不报错的失败"：

数据文件是逗号分隔，建表时忘了写 FIELDS TERMINATED BY ','。查询结果是这样的——

id    name      age
1     NULL      NULL
2     NULL      NULL

只有第一列有值，其余全 NULL，而且不报任何错。因为整行被当成一个字段塞给了 id（类型不符，于是 NULL），后面几列找不到分隔符，自然是 NULL。

看到"只有第一列有值"，第一个该怀疑的就是分隔符没配对。这个症状在排查清单里应该排第一位。

为什么用 \001 这么怪的字符？因为它几乎不可能出现在真实文本里。用逗号当默认值，一旦数据内容本身含逗号就会错位，而 \001 是真正的"不可能冲突"。代价是用文本编辑器打开这类文件会看到一堆小方块。

多字符分隔符不支持

Hive 的 LazySimpleSerDe 只支持单字符分隔符。源数据是 ||、\t\t 这类多字符时，处理办法是：用 MultiDelimitSerDe（建表时 ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.MultiDelimitSerDe'），或者干脆在入仓前用脚本替换成单字符。

（10、13 两集；多字符分隔符为补充）

4.6 内部表与外部表：DROP 到底删什么

建表语句的差异只有两个词：

-- 内部表（不写 EXTERNAL 就是内部表）
CREATE TABLE t_students_internal (
    id INT, name STRING
)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';

-- 外部表：多 EXTERNAL，几乎总要显式写 LOCATION
CREATE EXTERNAL TABLE t_students_ext (
    id INT, name STRING
)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
LOCATION '/stu';

为什么外部表几乎总要写 LOCATION：因为外部表的用途就是"接管一份别人已经在用的数据"，那份数据不会正好躺在 Hive 自己编出来的默认路径上。

操作内部表外部表
DESC FORMATTED 里的 Table TypeMANAGED_TABLEEXTERNAL_TABLE
DROP TABLE 删元数据✅✅
DROP TABLE 删 HDFS 数据✅ 一起删掉❌ 保留
删完之后表和数据都没了表看不见了，数据一个字节没少
一个比喻：外部表的 DROP 是"摘掉眼镜"——表看不见，东西还在原地；重新 CREATE EXTERNAL TABLE ... LOCATION 一次，数据立刻回来。内部表的 DROP 是"连人带行李一起扔了"。

为什么这么设计：Hive 不知道外部表 LOCATION 指向的目录还有没有别人在用——可能是 HBase 的目录、Spark 正在读的共享目录、别的部门的数据集市、或者从 Oracle 抽过来的原始落地文件。擅自删掉，损失的不是一张表，而是跨系统的数据事故。所以外部表的设计哲学是：我不拥有这份数据，我只借用，我无权删除。

生产怎么选

数据性质用什么原因
原始数据 / ODS 落地外部表一份数据多引擎共用（Hive / Spark / Presto），删表不能删数据；出问题只重建元数据，秒级恢复
数仓中间结果 / 临时汇总内部表数据是 Hive 自己算出来的，生命周期就该跟着表走，DROP 顺手清理能省空间
需要频繁重建的表外部表重建不用重新灌数据

一句话：原始数据一律外部表，中间结果用内部表。实际工作中大部分表是外部表，因为真实项目里绝大多数表都是接上游数据的。

4.7 分区表：分区就是目录

先看没有分区时的问题。课程做了一个实测：一张几十万行的表，SELECT * WHERE 某个条件，跑了很久——因为它必须全表扫。

建分区表

CREATE TABLE t_order (
    order_id STRING,
    amount   DOUBLE
)
PARTITIONED BY (dt STRING)              -- 分区字段写在括号外！
ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';
PARTITIONED BY 里的字段不是表里的真实列，它是目录名。

两个直接推论：① 分区字段不能和表字段重名；② 数据文件里不需要也不应该包含分区字段的值——那个值由目录名提供。

HDFS 上长这样：

/user/hive/warehouse/db.db/t_order/
├── dt=2026-01-01/000000_0
├── dt=2026-01-02/000000_0
└── dt=2026-01-03/000000_0

为什么分区能快：目录级裁剪

SELECT * FROM t_order WHERE dt='2026-01-02' 时，Hive 只打开 dt=2026-01-02/ 这一个目录，另外两个目录压根不碰。这叫分区裁剪（partition pruning）。

裁剪的依据是"WHERE 里出现了分区字段"这个语义，与它写在 WHERE 的第几个位置无关。

很多人以为"分区条件要写前面"，那是 Oracle 时代留下的误解。不写分区条件才是灾难——那就是全表扫所有目录，分区白建了。

静态分区导入

LOAD DATA LOCAL INPATH '/root/order_0101.txt'
INTO TABLE t_order PARTITION (dt='2026-01-01');

静态的意思是：分区值由你手写指定。适合"一个文件正好属于一个分区"的场景。

分区表不能用 hadoop fs -put 直接上传文件。

文件会落在表的根目录下，dt=xxx 子目录不会自动生成，查询直接 0 行。必须用 LOAD DATA ... PARTITION，或者手动建好目录再用 MSCK 修复（见 4.10）。

多重分区

PARTITIONED BY (year STRING, month STRING, day STRING)
/t_order/year=2026/month=01/day=01/

就是多级目录。注意分区字段的顺序会影响目录层级，实战中常见的组合是"先粗后细"（年/月/日、省/市），因为查询时通常先按粗粒度筛。

（15、16、20 三集）

4.8 动态分区：让 Hive 自己决定往哪写

静态分区一次只能写一个分区。真实场景常常是"一份数据里混着几十个日期"，这时要用动态分区。

-- ① 必须先开参数（默认是 false，不开直接报错）
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;

-- ② 分区值来自 SELECT 的最后一列
INSERT INTO TABLE t_order PARTITION(dt)
SELECT order_id, amount, dt FROM t_order_tmp;
最致命的坑：分区字段必须是 SELECT 的最后一列。

Hive 是按位置匹配的，不是按名字。上面这句里，SELECT 出来的第 1 列给 order_id、第 2 列给 amount、第 3 列给分区字段 dt。顺序错了不会报错，只会把数据写进错误的分区——而且很难发现。

另一个坑：默认分区数上限。Hive 默认限制单次写入的动态分区数量，超了会失败：

SET hive.exec.max.dynamic.partitions = 10000;              -- 总上限
SET hive.exec.max.dynamic.partitions.pernode = 10000;     -- 每个 MR 任务的上限

两个要成对调大——只调一个，另一个还会拦你。

静态分区动态分区
分区值从哪来手写常量查询结果的最后一列
一次写几个分区1 个N 个（由数据决定）
要不要开参数不要要，三个

4.9 分桶表：hash % N 带来的三个推论

分区是把数据拆成 目录，分桶是把数据拆成 文件。字段性质也不同：分区字段是虚拟的（目录名），分桶字段是表里的真实字段。

CREATE TABLE t_bucket (
    id INT, name STRING, state STRING
)
CLUSTERED BY (state) INTO 5 BUCKETS          -- 按 state 分 5 个桶
ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';

数据怎么进桶

SET hive.enforce.bucketing = true;       -- 必须开，否则桶数不对

INSERT INTO TABLE t_bucket
SELECT id, name, state FROM t_source
CLUSTER BY state;                        -- 必须用 INSERT SELECT
分桶表的数据只能用 INSERT ... SELECT 导入，LOAD DATA 无效。

因为要过一遍 hash % N 才知道每行该进哪个文件，纯文件搬移做不到。落地后目录里是 000000_0 ~ 000004_0 五个文件。

原理与三个推论

bucket_id = hash(分桶字段值) % 桶数

举例（3 个桶）：Tom 的 hash 是 7 → 7%3=1 → 1 号桶；rose 是 8 → 2 号桶；Jack 是 9 → 0 号桶。取模结果恒在 0 ~ N-1，永远不溢出。

注意：分桶不是平均分。桶内行数由哈希分布决定，两个不同的 key 也可能落到同一个桶。所以分桶不能解决数据倾斜——某个热点 key 在哪个桶，那个桶依然很大。

从"同一个 key 永远进同一个桶"这一点，能推出三件事：

推论带来什么前提
① 同 key 同桶JOIN 只需桶对桶比对，不用全量笛卡尔；小桶可装进内存退化成 Map Join，省掉 reduce 端 shuffle两表同一 join key 分桶、桶数相同（或整数倍）
② 数据被打散成 N 份采样快：TABLESAMPLE(BUCKET 1 OUT OF 5) 直接取文件，读 1/5 数据即可，不用全表扫再 LIMIT表已分桶
③ 桶内有序可二分查找；两表同列 SORTED BY 时可做 SMB Join（归并即可，连哈希表都不用建）建表时加了 SORTED BY (col)

对哪些查询没提升（这是常见误解）：普通的 WHERE 过滤、GROUP BY 聚合——这两类不会因为分了桶就变快。分桶只对"按分桶列做等值连接"和"抽样"有效。

（21~24 四集；"对 group by 无提升"为补充澄清，课程原话有出入）

4.10 表维护与数据进出

ALTER TABLE：只改元数据，不动数据

ALTER TABLE t RENAME TO t_new;                        -- 改表名
ALTER TABLE t ADD COLUMNS (city STRING);           -- 加列（只能加末尾）
ALTER TABLE t CHANGE COLUMN age age2 INT;          -- 改列名/类型
ALTER TABLE t REPLACE COLUMNS (id INT, name STRING);-- 整表替换列
ALTER TABLE t SET TBLPROPERTIES ('k'='v');
ALTER TABLE 一个字节的数据都不改，只改 MySQL 里的元数据。

后果很严重：你改了一个列名或类型，旧分区里的文件还是旧格式。下次查询会按新 schema 去读旧文件，结果要么全 NULL、要么数字全错——能跑，但结果错，这是最难发现的一类故障。

三条硬限制：加列只能加在末尾；不能删单列，只能 REPLACE COLUMNS；有数据时用 AFTER / FIRST 挪位置必报错。所以字段顺序错了，正确做法是 DROP 重建表再灌一次，不是 ALTER 硬挪。

修复分区：MSCK REPAIR TABLE

这是实战里每周都会遇到的场景。数据已经在 HDFS 上按分区目录摆好了（Flume 落的、Spark 写的、同事 hdfs dfs -put 上去的），你要建表挂上去：

/user/hive/warehouse/itdkma/t_date_part/
├── dt=20240425/data.txt
├── dt=20240426/data.txt
└── dt=20240427/data.txt
CREATE EXTERNAL TABLE t_date_part (
    id INT, name STRING, age INT
)
PARTITIONED BY (dt STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
LOCATION '/user/hive/warehouse/itdkma/t_date_part';

建完 SHOW PARTITIONS 一看——空的。查询 0 行。

核心认知：HDFS 上有目录 ≠ Hive 里有分区。

LOCATION 只是告诉 Hive"表的根目录在这儿"，它不会去扫这个目录下有哪些子目录，更不会自动注册成分区。metastore 的 PARTITIONS 表里一行记录都没有。

这是两套独立的东西，必须同步。同步命令：

MSCK REPAIR TABLE t_date_part;

执行完再 SHOW PARTITIONS，三个 dt=... 全部出现，立刻能查到数据。它做得很快，因为它只操作元数据——扫描 HDFS 目录、把缺失的分区信息补进 metastore。

两个限制：MSCK 只补不删（HDFS 上删了目录，metastore 里的分区记录还在，要用 DROP PARTITION）；目录名必须是 字段=值 的格式，写成 dt_20240425 这种会修不动，报 code 1——九成的 code 1 是目录名不规范（下划线代替等号、大小写不一致、带特殊字符）。

LOAD DATA：四种组合

LOAD DATA [LOCAL] INPATH '<path>' [OVERWRITE] INTO TABLE tb
[PARTITION (p1=v1)];
写法数据从哪来源文件目标表
①LOCAL ... INTO客户端本地（Linux）复制，保留追加
②LOCAL ... OVERWRITE客户端本地复制，保留覆盖
③INPATH ... INTOHDFS移动，消失追加
④INPATH ... OVERWRITEHDFS移动，消失覆盖
最关键的一条：带 LOCAL 是 cp，不带 LOCAL 是 mv。

不带 LOCAL 时，HDFS 上的源文件会被移走、消失。由此产生两个真实事故：

① 路径写成了别的表的数据目录 → 那张表的数据被"搬空"，Hive 不拦你，因为它认为你在移动文件，完全合法。
② 源路径是多个作业共用的落地目录 → 第一个作业跑完文件就没了，后面的全读不到。共用目录一律先 cp 一份再用。

追加 vs 覆盖：追加不去重，跑两遍就有两份数据（文件名冲突时自动改名加后缀，不会覆盖）。OVERWRITE 对分区表是"只覆盖指定分区"，不影响其他分区——这点很关键，意味着可以按天重跑某个分区而不动历史。

导出与多重插入

-- 导出到 HDFS 目录（结果是多个文件，因为并行写）
INSERT OVERWRITE DIRECTORY '/export/out'
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
SELECT * FROM t_order;

-- 导出到本地目录要加 LOCAL（Hive 3 支持）
INSERT OVERWRITE LOCAL DIRECTORY '/root/out' ...

-- 多重插入：一次扫描源表，写入多个目标表
FROM t_source
INSERT OVERWRITE TABLE t_a SELECT id, name WHERE type='a'
INSERT OVERWRITE TABLE t_b SELECT id, name WHERE type='b';
多重插入解决的是"重复扫描"：如果分两条 INSERT ... SELECT 写，源表要被扫两遍。多重插入只扫一遍，把结果分发给多个目标表——源表越大，省得越多。限制是必须配合 FROM 子句用（语法就是上面这个形状）。

这一章的三条主线

① 解析线（4.4 / 4.5）：Hive 的表是虚拟的，ROW FORMAT 就是 SerDe 配置。默认分隔符是 \001，配错的表现是"只有第一列有值、不报错"。

② 归属线（4.6 / 4.7 / 4.9）：内部表还是外部表决定 DROP 删不删数据；分区把数据切成目录（按目录裁剪）；分桶把数据切成文件（按 hash 对齐 join）。分区是"少读"，分桶是"少算"。

③ 一致性线（4.2 / 4.10）：元数据在 MySQL、数据在 HDFS，两套系统。乱码、MSCK、ALTER 只改元数据、LOAD DATA 的移动语义——全都源于这两套系统不同步。遇到"数据明明在却查不到 / 能跑但数字不对"，先想这一条。
