01 · Hadoop 基础与集群架构

这一章要解决三件事：看懂 Hadoop 的架构图、能在三台机器上搭起一个集群、跑通第一条数据链路。前四节是地图（不涉及操作），中间两节是动手，最后两节建立"数据在集群里怎么流动"的直觉。如果你只想快速搭起来，至少先读 1.4 和 1.6——那里有三台机器的角色分配和最常遇到的八个报错。

内容基准 主体素材：Hadoop 实战课第 08 天（录制版本 Hadoop 3.3.0、JDK 1.8、CentOS 7 系）　·　2026-11 提炼 需留意：1.5 / 1.6 涉及具体版本号、下载地址、配置文件路径，请以你实际安装的发行版为准；1.1~1.4、1.7~1.8 是架构与方法论，不受版本影响。原课有 2 个"回顾"视频已跳过。

1.1 Hadoop 是什么：两层含义，两件事

先说最容易含混的地方。"Hadoop"这个词在日常对话里有两个所指，混着用会让人误解你的水平。

狭义的 Hadoop：Apache 旗下一个用 Java 写的开源软件，它的全部使命就两件事——海量数据存得下、海量数据算得动。落到工程上，是三个组件：

组件管什么一句话理解
HDFS海量数据存储把多台机器的硬盘"打通"，对外像一个盘
MapReduce海量数据计算把一个大计算拆到多台机器上并行跑
YARN资源调度多个任务抢 CPU/内存时，由它统一分配（2.0 之后才有）

YARN 单独说一句，因为初学者最容易把它当成"计算的"。它本身不存数据，也不算数据——它是个记账的。一个集群不可能只跑一个任务，任务来了要申请多少内存、多少 CPU，谁先谁后，得有本账。这本账就是 YARN。

广义的 Hadoop：围绕上面那三件套长出来的整个生态圈——Hive 做 SQL、HBase 做列存、Sqoop 搬数据、Flume 收日志、ZooKeeper 做协调、Spark/Flink 做更快的计算。

面试和工作中说"Hadoop"，八成指广义。有人说"我们用 Hadoop 做数仓"，那一定不是指那个 tar.gz，而是指 HDFS + Hive + YARN 这一整套。搞清楚这个区别，沟通时不会答错方向。

为什么需要它？一个具体量级：中国移动北京在 2016 年，单日数据量约 2 TB。单块硬盘装不下，换更贵的机器不划算，唯一的出路是把一堆普通机器串起来。这就是 Hadoop 的全部出发点——不是"技术先进"，是"便宜且能扩容"。

1.2 发展史与版本演进：每一代补了哪个洞

从"存不下"到 Google 的三篇论文

主角是 Doug Cutting，Hadoop 之父。他当时在 Yahoo 做搜索引擎，手上项目叫 Nutch——干的就是爬虫那套活：抓网页、落库、清洗、分类、供检索。

然后撞上第一个瓶颈：存不下。爬到数十亿网页，而 2004/2005 年主流硬盘只有 40G / 80G，换超大型数据库也无解，项目卡了很久。

转机是 Google 发表的一篇论文：GFS（Google File System）——把多台计算机串起来共同对外提供存储，数据切成一块一块、每台分担一部分。Cutting 据此写出了第一个组件 HDFS。

第二个瓶颈：算不动。数据散在几十台机器上，怎么汇总、怎么分类？Google 第二篇论文 MapReduce 给了答案（分布式数据处理 + 超大型集群管理）。照此写出了 MapReduce。

2006 年项目定名 Hadoop，2008 年整体捐给 Apache 软件基金会，成为顶级项目。

第三篇论文 BigTable 是另一条支线：关系型数据库在海量数据下撑不住，Google 自研 BigTable，业界据此做出了 HBase。

这套组合拳面试问得非常多：Hadoop 之父是 Doug Cutting；起源项目叫 Nutch；受 Google 三篇论文（GFS / MapReduce / BigTable）启发；2008 年归入 Apache。四个点，一个都别错。

版本演进：三代的差别只在"有没有 YARN"

这是本节最值钱的一条线。别看版本号唬人，骨架其实早就定型了：

Hadoop 1.x        HDFS（存储） + MapReduce（计算）            # 两个组件
Hadoop 2.x        HDFS（存储） + YARN（调度） + MapReduce      # 三个组件
Hadoop 3.x        HDFS + YARN + MapReduce                    # 组件不变，只是优化

1.x 的病根在哪：存储和计算是分开的两块，但"资源管理"没有独立出来，被焊死在 MapReduce 内部——谁跑任务谁自己管机器。后果是集群被绑死成"只能跑 MapReduce 的集群"。你想上 Spark、Impala、Flink，没有公共的地方申请资源，只能各建一套集群。

2.x 怎么治的：把"资源调度"从计算框架里剥出来，做成独立的一层 YARN。计算框架变成 YARN 上的租户，谁都可以来申请资源。这才让"一个物理集群跑多种计算引擎"成立——也是今天 Spark on YARN、Flink on YARN 的前提。

3.x 改了什么：讲者原话是"2.0 和 3.0 从底层架构来说只是做了一些性能优化，组件上没有什么太大变化"。所以别被版本号吓住，三件套的骨架从 2.x 就定型了。3.x 的具体增益在 1.3 详说。

一句话记住三代：只能存 → 能存能算 → 能存能算还能被多方共用。判断一个集群是几代，看有没有 YARN 就够了。

发行版：为什么企业用的不是 Apache 版

能下载到的都叫"发行版"，分两大类：

Apache 社区版商业版（CDH / HDP）
迭代速度快，新特性先上慢，求稳
稳定性一般好，经过厂商测试与打包
跨版本兼容差：3 不一定兼容 2好，下一版通常兼容上一版
运维配套自己拼自带管理平台、监控、工单
成本完全免费部分服务收费

两个名字要认准：CDH（Cloudera Distribution including Apache Hadoop）与 HDP（Hortonworks Data Platform）。HDP 已被 Cloudera 收购，现在是同一家公司的两条产品线。补一个事实：Doug Cutting 本人就在 Cloudera 任职，所以 CDH 可以认为是商业版里最正统的那一支。

企业实际怎么选：生产要稳、要有人兜底，所以商业版更常见；学习与验证用 Apache 版最快，能看到最原始的样子。这门课就是这个安排——基础阶段用 Apache 3.3.0，到项目阶段再上商业版。

一条铁律：集群里所有节点的发行版与版本必须完全一致。Apache 版跨大版本混用基本必炸（配置项名、jar 包结构都有差异）。别把 2.x 的配置往 3.x 上抄。

1.3 三代架构：从"一个大脑"到"职责拆分"

1.2 讲的是版本编号，这一节讲图上到底画了几个框。看懂这三张演进的图，后面所有的角色、进程、报错才有归属。

Hadoop 1.x：JobTracker 一肩挑

Hadoop 1.x
├── HDFS 集群（主从）
│   ├── NameNode           ×1    元数据（目录树 + 块映射），不存真实数据
│   ├── SecondaryNameNode  ×1    辅助合并 edits → fsimage，不是备份
│   └── DataNode           ×N    真实数据块，心跳 + 块汇报
└── MapReduce 集群（主从）
    ├── JobTracker         ×1    接任务 + 分任务 + 资源调度  ← 全集群唯一
    └── TaskTracker        ×N    执行 JobTracker 派下来的 Task

JobTracker 干三件事：接收客户端作业、把作业拆成 Task 往下分、按任务需求分配 CPU/内存。问题也出在这里——它一个人干了三份活，而且有且只有一个。

由此产生三个后果，正是后面每一代要解决的：

  1. 单点故障：JobTracker 挂了，整个集群无法再对外提供计算服务。
  2. 职责过重：资源调度和任务生命周期耦合在一个进程里，集群一大它就是瓶颈。
  3. 只能跑 MapReduce：资源被 MR 独占，别的计算框架进不来。

Hadoop 2.x：把"管资源"和"管任务"拆开

Hadoop 2.x / 3.x
├── HDFS 集群（未改动）
│   ├── NameNode          ×1（HA 时 2；3.x 支持多 NN）
│   ├── SecondaryNameNode / Standby NameNode
│   └── DataNode          ×N
├── YARN 集群（主从）
│   ├── ResourceManager   ×1（HA 时 2）  只管全集群资源 + 接作业
│   ├── NodeManager       ×N            单机资源管理 + 拉起/监控 container
│   └── ApplicationMaster 每作业 1 个   该作业的"小 JobTracker"
└── MapReduce —— 不在架构图上：客户端 jar + AM/Task 代码

JobTracker 的职责被拆到了哪，这张表建议记住，画架构图和面试都用得上：

1.x 里 JobTracker 干的活2.x 落到谁头上
全集群资源管理与分配ResourceManager
接收作业、拆任务、调度单个作业ApplicationMaster（每个作业一个）
在机器上启进程、监控任务NodeManager + container
TaskTracker 本身被 NodeManager + container 取代，不再有独立常驻角色
"2.x 没有 MapReduce 集群了"是口头简化，别照着画图。MapReduce 组件仍然存在，但它不再是物理角色，而是逻辑角色 / 代码。提交一个 MR 作业，是把 jar 交给 ResourceManager，RM 调度给 NodeManager 去跑。所以架构图上不要给 MapReduce 画第三个框、也不要画它的常驻进程——这个错误非常常见。

Hadoop 3.x：架构没变，补的是"单点"和"效率"

2.x 拆掉了 JobTracker 这个单点，但NameNode 还是单点——"NameNode 坏了 HDFS 就坏了"。3.x 从这一层往下补。架构组成和 2.x 完全一样，改的是这些：

3.x 的变化解决什么问题
多 NameNode 支持NN 单点：从"一个 NN"变成可多 NN
EC 纠删码（Erasure Coding）三副本存储开销大：用校验块换空间
多个 ResourceManagerRM 单点：做主备 HA
MapReduce 本地化优化、内存参数自动推断减少网络传输、免去手调内存
YARN Timeline Service V2、队列配置增强作业历史查询、多租户队列管理
两个特别容易混的点，面试爱考：

① 多 NameNode ≠ 联邦（Federation）。3.x 的"多 NN"同时服务于两种场景——HA（2 个 NN 主备，同一份命名空间）和 Federation（多个 NN 各管独立命名空间）。课程只说了"支持多个 NameNode"，没区分这两者。

② 多 ResourceManager 不是 3.x 独有。讲 2.x 的 YARN 时就已经说"RM 可以有多个，将来做高可用"。

1.4 集群角色与部署：三台机器怎么分

先记住一句话：只有两个集群

HDFS 集群 + YARN 集群，就这两个。两者逻辑上分离（画图是两个独立的框，互不依赖、互不影响），物理上在一起（机器不够时，NameNode 和 ResourceManager 装同一台，DataNode 和 NodeManager 装同一台）。

这句话解释了一个常见困惑：为什么架构图上是两个框，jps 出来的进程却混在同一台机器上。因为图讲的是逻辑职责，部署讲的是物理位置，两者不必一致。

角色总表：谁管什么，挂了会怎样

角色进程名职责通常几个挂了会怎样
NameNodeNameNode管理元数据（目录树、块→DN 映射），不存真实数据1（HA 时 2）HDFS 整体不可用：读写全停（数据块还在 DN 上，但没人知道怎么拼）
DataNodeDataNode存真实数据块，定期向 NN 发心跳、汇报块列表每台工作机 1 个单台挂由副本兜底；同时挂掉的数量超过副本数才丢块
SecondaryNameNodeSecondaryNameNode辅助合并 edits 到 fsimage，做检查点1（必须与 NN 分机）不影响集群运行，只影响检查点；不能顶替 NN
ResourceManagerResourceManager全集群资源管理、接收作业、分配 container1（HA 时 2）YARN 不可用：新作业提交不了
NodeManagerNodeManager单机 CPU/内存管理，按 RM 指令拉起并监控 container每台工作机 1 个该机器上的任务失败、资源被摘出池；HDFS 侧不受影响
ApplicationMasterMRAppMaster 等单个作业的调度：向 RM 申请资源、与 NM 协商起 container、监控 Task每作业 1 个该作业失败，RM 会重新拉起 AM
SecondaryNameNode 这个名字骗了很多人。它不是 NN 的备机，也不负责备份。它是个"助手"，定期把 NN 的编辑日志（edits）合并进镜像（fsimage），减轻 NN 启动时的压力。只有特别紧急时才拿它恢复数据，而且会丢一部分。真正的 NN 热备叫 Standby NameNode（HA 方案）。

三台机器怎么分（经典面试题）

题目：给你 3 台机器，画出 Hadoop 架构图并说明每台跑哪些角色。

机器部署的角色数量理由
node1NameNode + ResourceManager + DataNode + NodeManager4两个"主"放一起省机器；工作角色每台都有
node2SecondaryNameNode + DataNode + NodeManager3SNN 必须与 NN 分机：两者都吃内存
node3DataNode + NodeManager2纯工作节点，提供存储 + 算力

三台合计 9 个进程。这个数字后面会用到——1.6 讲排错时，jps 的输出就是拿它比对。

为什么 SNN 必须和 NN 分开？两个都吃内存、都在管元数据。放一台机器上，内存很快耗光；机器一挂，元数据全没，整个集群直接瘫痪。NN 是集群的核心，不能和它的助手绑在一条船上。

四种部署方式：怎么判断、什么时候够用

模式机器数怎么判断用在哪
本地模式1jps 看不到 NameNode/DataNode 等守护进程，读写的是本地文件系统调 MR 代码逻辑、跑小数据、入门 demo
伪分布式1jps 能看到 NameNode/DataNode/RM/NM学配置、验证 HDFS 与 YARN 行为、单机联调
完全分布式≥3角色分布在多台主机，走真实网络课程重点 + 生产环境
HA 高可用集群 + 冗余NameNode 2 个、RM 2 个，存在主备切换生产必备：一台故障不影响集群
什么时候伪分布式就够？只在一台机器上、只为跑通流程或验证配置时够用。一旦要验证多节点、数据本地性、副本分布、HA 切换、性能，就必须上完全分布式——伪分布式根本模拟不出来，因为它只有一个 DataNode，"副本放三台机器"这件事在它身上不存在。

装哪个包：源码包（src）需要自己编译，流程复杂；编译好的 binary 包直接装。课程用后者，版本 Hadoop 3.3.0。面试常问"你们用的什么版本"，对版本号要有概念。

1.5 环境准备与四个核心配置

前面四节都是地图。从这里开始动手。先说清楚动手之前的四个前提，缺一个后面都会卡：

  1. 三台机器，主机名 node1 / node2 / node3，且每台的 /etc/hosts 里有另外两台的名字映射。这一步不做，后面所有"写主机名"的配置都会失败。
  2. SSH 免密登录：node1 能免密 ssh 到 node2/node3。因为 start-dfs.sh 的原理就是 ssh 到 workers 名单里的每台机器去拉进程。
  3. JDK 1.8 装好，java -version 有输出。
  4. 防火墙与 SELinux 关闭（学习环境），否则 9870 / 8088 页面打不开。

要改的六个文件

全部在 $HADOOP_HOME/etc/hadoop 下：

文件管什么本节改什么
hadoop-env.shHadoop 自己的环境变量JAVA_HOME + 5 个启动用户
core-site.xml全局/核心配置（面试常问"哪个是核心文件"，答案是它）文件系统入口、临时目录
hdfs-site.xmlHDFS 专属SecondaryNameNode 放哪
mapred-site.xmlMapReduce 专属跑在 YARN 上、历史服务器
yarn-site.xmlYARN 专属RM 在哪、shuffle、日志聚集
workers集群有哪几台三台主机名
配置的逻辑是"只在 node1 改，改完 scp 覆盖过去"。所以 node1 改错 = 三台全错 = 集群起不来。反过来也有好处：看到"三台同时少同一个进程"，第一反应就该是配置错了，而不是一台台去修。

① hadoop-env.sh：告诉 Hadoop JDK 在哪

在文件末尾追加（不是在开头改注释）：

export JAVA_HOME=/export/server/jdk1.8.0_241

# 3.x 起强制要求：启停脚本会 ssh 到各节点执行命令，必须显式声明用哪个用户跑
export HDFS_NAMENODE_USER=root
export HDFS_DATANODE_USER=root
export HDFS_SECONDARYNAMENODE_USER=root
export YARN_RESOURCEMANAGER_USER=root
export YARN_NODEMANAGER_USER=root

两处容易错：JAVA_HOME 要写绝对路径，不要写 $JAVA_HOME——脚本执行时机可能拿不到你 profile 里导出的值，报 JAVA_HOME is not set。另外那 5 个 USER 是 3.x 才强制的，2.x 教程里没有，照抄 2.x 会漏。

② core-site.xml：两个改错就要命的属性

<configuration>
    <property>
        <name>fs.defaultFS</name>
        <value>hdfs://node1:8020</value>
    </property>
    <property>
        <name>hadoop.tmp.dir</name>
        <value>/export/data/hadoop-3.3.0</value>
    </property>
    <property>
        <name>hadoop.http.staticuser.user</name>
        <value>root</value>
    </property>
</configuration>

fs.defaultFS 为什么必须写主机名而不是 localhost？

这是整个 Hadoop 的文件系统入口，客户端（hdfs dfs -put、Java API、Hive）全靠它找集群。关键在于：这个值会被写进 NameNode 返回给客户端的元数据里。你写 localhost，客户端就会去连它自己的 8020——在 node2 上执行命令直接 Connection refused。写 127.0.0.1 同理。

hadoop.tmp.dir 不配会怎样？它是 Hadoop 的本地工作目录，NameNode 的 fsimage/edits、DataNode 的数据块默认都往这下面放。不配就落在 /tmp 下，而 /tmp 会被系统定期清理（常见 30 天），一旦被清，NameNode 元数据全丢 = 集群数据全没。这是"跑了两天突然起不来"的头号原因。目录不用手动建，第一次 format 会自动生成。

③ hdfs-site.xml：只改一个，SNN 在哪

<configuration>
    <property>
        <name>dfs.namenode.secondary.http-address</name>
        <value>node2:9868</value>
    </property>
</configuration>

NameNode 在 node1（由 fs.defaultFS 决定），SecondaryNameNode 放 node2。SNN 必须独立一台机器——两者都吃内存，放一起既抢资源又失去容错意义。

注意 dfs.replication（副本数）这里没配，因为默认就是 3，而我们正好 3 台机器。

④ mapred-site.xml：三个最容易漏的 HADOOP_MAPRED_HOME

<configuration>
    <property>
        <name>mapreduce.framework.name</name>
        <value>yarn</value>
    </property>
    <property>
        <name>mapreduce.jobhistory.address</name>
        <value>node1:10020</value>
    </property>

    <property>

mapreduce.framework.name=yarn 决定任务提交给谁。默认是 local，也就是单机跑，跟集群没关系——忘了改这个，你会发现"作业能跑但 8088 上看不到"。

两个历史服务器端口别混：10020 是内部 RPC（客户端和 AM 写作业历史用），19888 是给人看的 Web UI。

最后三组 HADOOP_MAPRED_HOME 是最容易漏的。YARN 拉起的容器里没有你的环境变量，必须显式告诉它 Hadoop 装在哪，否则任务直接失败，报 HADOOP_MAPRED_HOME is not set。这三行在 2.x 教程里通常没有，是 3.x 加上去的。

1.6 启动与排错：jps 是你的第一双眼睛

format：只做一次，只在一台机器上做

hdfs namenode -format

为什么必须先 format？因为数据目录根本还不存在。这条命令做的事是：在 NameNode 上初始化元数据目录（建 dfs/name，写入初始的 fsimage 和 clusterID）。

判断成功的三个信号：末尾有 Storage directory ... has been successfully formatted、退出码是 0、dfs/name 目录被创建出来了。

这条命令在生产环境执行完应该被拉出去。它相当于把放元数据的目录清掉——元数据没了，HDFS 里存的所有文件就都找不回来了（数据块还在 DataNode 磁盘上，但没人知道它们拼起来是什么文件）。

重复 format 到底会发生什么，这是新手最常废掉集群的操作，机制值得看清：

  1. 第二次 format 重新生成 dfs/name，写了一个全新的 clusterID。
  2. 但 dfs/data/current/VERSION 里还留着第一次的 clusterID，DataNode 的数据没被清过。
  3. 启动 DataNode 时它拿自己的 clusterID 去比对 NameNode 的，对不上，拒绝加入：Incompatible clusterIDs。
  4. 结果是 NameNode 起得来、DataNode 全起不来——jps 里只有 NameNode，9870 页面 Live Nodes 为 0，HDFS 处于"能看不能存"的状态。

想重来的正确姿势（顺序不能反）：

stop-all.sh                          # 1. 先全停，别带着半死进程删文件
jps                                  # 2. 三台都确认没有残留进程，有就 kill
rm -rf /export/data/hadoop-3.3.0/dfs        # 3. node1 删整个 dfs
rm -rf /export/data/hadoop-3.3.0/dfs/data   #    node2/node3 删 data
rm -rf $HADOOP_HOME/logs                    # 4. ★ 连 logs 一起删
hdfs namenode -format                       # 5. 回 node1 重新 format，只做一次
为什么必须连 logs 一起删？日志是追加写的。你重来一遍之后去 tail 日志，看到的第一屏很可能还是上次失败的旧报错（比如那个已经修好的 clusterID 不一致），于是你去修一个根本不存在的问题，越修越乱。删掉 = 保证这次启动的日志只属于这次。这是最容易漏的一步。

启动：三种方式，按场景选

start-all.sh                              # 一次性全起（学习期最常用）
start-dfs.sh && start-yarn.sh              # 分开起（推荐：出问题好定位）
hdfs --daemon start datanode              # 单独起某一个（排错时用这个）

启动过程中终端会刷一堆 starting namenode, logging to ...，这不是报错。真正的错误会带 ERROR 字样或异常堆栈。

jps 自检：这个集群到底该有几个进程

jps 就是"看当前机器的 Java 进程"。Hadoop 每个组件都是一个 JVM 进程，所以它是最快、不依赖任何页面和配置的自检手段。三台各敲一次，对着这张表看：

机器该有的进程个数
node1NameNode、DataNode、ResourceManager、NodeManager4
node2SecondaryNameNode、DataNode、NodeManager3
node3DataNode、NodeManager2
合计9

口诀：NameNode 只在 node1、SecondaryNameNode 只在 node2、ResourceManager 只在 node1；DataNode 和 NodeManager 每台都有。另外每台的 jps 输出里会多一行 Jps 自己，属正常。

排错：先分层，再看关键字

老师给的不是"报错大全"，而是一条固定路径。记住这条，任何启动失败都能走下去：

① 终端启动输出里有没有 ERROR？
   ├── 有 → 它通常已经把「哪个文件、第几行」打出来了，直接去改配置
   └── 没有 → 往下
② jps 少哪个进程？
   ├── 缺 → ③
   └── 不缺但页面打不开 → 查端口 / 防火墙 / hosts
③ 手工单独启那一个进程（hdfs --daemon start xxx），看它自己报什么
   ├── 起来了 → 集群级脚本问题（workers 文件 / ssh 免密）
   └── 起不来 → ④
④ 去 $HADOOP_HOME/logs/ 看「和它同名」的日志

第 ④ 步的对应关系：哪个服务起不来就看哪个日志，日志文件名里带服务名。比如 node2 的 DataNode 没起来，就看 hadoop-hdfs-datanode-node2.log。看的时候先看 .log 的尾部——最新的错误在最后。.out 是标准输出，.log.1 是滚动的历史文件。

八个最常见的报错

按"现象 → 原因 → 解法"整理。括号里是判据关键字，看到这几个词就该往那个方向想。

E1 · 启动到 SecondaryNameNode 时抛 SAXParseException

现象：NameNode、DataNode 看着都正常启动了，到 SNN 那一步突然炸，报 error parsing conf core-site.xml + lineNumber: 38 + must be terminated by the matching end-tag。

原因：XML 少了一个闭合标签。而 NameNode 恰好没读那个属性所以没报，SNN 读到了才炸——所以"前半段没报错"不代表配置对。

解法：别只看报的第 38 行，真正的错在它上面几行。改完先 stop-dfs.sh 再 start-dfs.sh（不能只重启失败的那个）。

自查捷径（视频没讲，但这招比启集群快得多）：python3 -c "import xml.dom.minidom; xml.dom.minidom.parse('core-site.xml')"，不报错就是格式对。

E2 · 某个进程就是没起来，但终端不报错

原因分三类：配置项错、端口冲突、依赖的上游没起来。

解法：手工启一次让错误暴露在自己眼前——hdfs --daemon start datanode，然后看日志。

判据：日志里出现 Retrying connect to server: node1:8020 或 Connection refused，说明它在连 NameNode 时失败，问题不在 DataNode 本身。处理顺序：node1 上 jps 有没有 NameNode → 没有就查 NameNode 日志 → 有就 telnet node1 8020 试端口。

E3 · 某台报 JAVA_HOME is not set

原因：环境变量只在第一台配了。安装包只传第一台是对的，但环境变量必须每台都配——配置文件可以 scp 分发，环境变量不会跟着走。

判据：那台机器敲 jps 只有一行 Jps，说明 JVM 都找不到。

E4 · Permission denied

原因：HDFS 也有 POSIX 权限，普通用户往 /（owner 是启动 NameNode 的用户）下写会被拒。

解法：写到自己的家目录 hdfs dfs -mkdir -p /user/$(whoami)，或学习环境直接 -chmod -R 777。

判据：报错里有 user=xxx, access=WRITE, inode="/":hadoop:supergroup:drwxr-xr-x，冒号后面就是当前 owner 和权限。

E5 · NameNode is not formatted

原因：压根没 format 就启动了，dfs/name 目录不存在。

解法：回上一节 format。注意——如果集群跑起来过、有数据了，就别再 format。

E6 · 三台全缺 DataNode，报 Incompatible clusterIDs

原因：重复 format 了。见本节开头的机制说明。

解法：停集群 → 删 dfs 和 logs → 重新 format 一次。

E7 · 进程全在，但 9870 打不开

三个可能：防火墙没关、hosts 没配（用主机名访问时解析不到）、看的是旧端口 50070（Hadoop 2.x 的端口，3.x 改成了 9870）。

E8 · 作业能跑，但 8088 上看不到

原因：mapreduce.framework.name 没改成 yarn，还是默认的 local。作业在单机上跑完了，YARN 根本不知道有这回事。

1.7 HDFS 初体验：块、副本、客户端

三个端口，各管一件事

端口是什么什么时候用它
9870NameNode 的 Web UI看文件系统、块分布、Live Nodes 数量
8088ResourceManager 的 Web UI看作业列表、状态、日志入口
8020NameNode 的 RPC 端口不是给人看的，客户端连它拿元数据

先把三个端口分清，能省掉一半的"页面打不开"困惑——9870 是 HDFS 的门面，8088 是 YARN 的门面，8020 是程序用的。

五个骨架命令

hdfs dfs -ls /                      # 列目录
hdfs dfs -mkdir -p /itcast          # 建目录（-p 递归）
hdfs dfs -put 本地文件 /itcast/       # 上传
hdfs dfs -cat /itcast/文件           # 看内容
hdfs dfs -get /itcast/文件 ./        # 下载到本地当前目录
hdfs dfs -rm -r /itcast              # 删除（-r 删目录）

注意前缀是 hdfs dfs，不是 hadoop fs（后者也能用，是旧写法）。这些命令操作的是集群上的文件，不是你本机的文件——这一点在第一次用时容易混。

块（block）：逻辑切分，不是物理预留

这是最容易被误解的一个概念。块大小是"每块的上限"，不是"每块的固定占用"。

文件大小块数各块大小
4 B14 B（不会真占 128 MB）
200 MB2128 MB + 72 MB
256 MB2128 MB + 128 MB
300 MB3128 MB + 128 MB + 44 MB

为什么偏偏是 128 MB？这不是拍脑袋，是"让磁盘尽量少寻道"的工程结论：机械盘一次寻道约 10 ms，顺序读约 100 MB/s。想让寻道开销占比压到 1% 左右，一块的大小 ≈ 传输速率 × 寻道时间 × 100 ≈ 100 MB，取 2 的整数次幂就是 128 MB。换句话说：块要大到"读完一整块的时间远大于寻道时间"，顺序读才划算。

为什么不是 64 MB：那是 Hadoop 1.x 的默认值。块数翻倍 → 元数据翻倍 → 切片翻倍 → 任务启动开销翻倍。

为什么不是 1 GB：块太大会有三个真问题——并行度塌了（一块通常对应一个 map 任务，1 GB 文件就只有 1 个任务，集群再大也用不上）、恢复粒度太粗（一次要重传的数据太多）、传输时间过长（中途失败的代价高）。

块大小可配（dfs.blocksize），但生产上基本别动。改了会让老文件和新文件的块尺寸混在一起，影响切片和均衡。知道"能改"就够了。

小文件为什么是灾难

NameNode 不存数据，只存元数据，而且全部放在内存里。一个文件（inode）加一个块，经验值各约 150 字节。算一下账：

场景元数据对象内存占用
1 个 200 MB 文件1 inode + 2 块≈ 450 B
100 万个小文件100 万 inode + 100 万块≈ 300 MB 常驻堆
1 亿个小文件1 亿 inode + 1 亿块≈ 30 GB 常驻堆
同样 200 MB 数据，存成 1 个文件只花 450 字节元数据；拆成 100 万个小文件要花 300 MB 堆——差了 70 万倍。NameNode 的堆是有限的（默认几 GB），千万级小文件就会把堆吃干，表现为频繁 Full GC、RPC 超时、集群"假死"；重启时还要把镜像全量加载进内存，启动时间从分钟级变成小时级。这就是"HDFS 不适合存小文件"的根因——不是存不下，是管不过来。

另外两个隐性成本：每个块都要定期向 NameNode 发块报告、每次读写都是一次 RPC，百万级小文件直接把 RPC 队列打满；MapReduce 一个切片一个任务，处理 1 KB 也要付几秒的启动开销。

对策方向（不用记全）：上传前合并成大文件、用 SequenceFile / ORC / Parquet 这类容器格式打包、历史数据打 HAR 归档。极端情况上 NameNode 联邦，但联邦只是分摊压力，不减少元数据总量。

副本：3 份放在哪，代价是什么

默认 dfs.replication = 3。我们这个 3 台机器的小集群，就是 node1 / node2 / node3 各一份。容错能力：可以同时容忍 2 台故障而不丢数据。

真实集群的放置策略（机架感知）不是随便扔：

  • 第 1 份：客户端所在节点（客户端在集群外时随机挑一个）。
  • 第 2 份：不同机架的随机节点。
  • 第 3 份：与第 2 份同机架的另一个节点。

也就是 1 份本机架 + 2 份跨机架。为什么这么设计？跨机架带宽是稀缺资源——读的时候就近读本机架那份最快；同时单个机架断电（交换机挂、机柜掉电）也只丢 1 份。课堂上 3 台机器通常同机架甚至没配拓扑，所以退化成"三台各一份"。

代价：存储利用率只有 1/3，写入网络放大 3 倍。200 MB 文件实际占 600 MB。

hdfs dfs -setrep -w 2 /itcast/文件      # 改成 2 副本并等待完成
hdfs dfs -setrep -R 2 /itcast           # 递归改整个目录

两点注意：副本数设得比节点数大没有意义（3 台最多 3 份）；副本因子设成 1 就等于没有冗余。

把块和副本合起来算一遍

200 MB 文件进 HDFS，会发生什么？这个问题面试和排障都爱问：

  • 块数：200 ÷ 128 = 1 余 72 → 2 个块（128 MB + 72 MB）。
  • 块副本数：2 块 × 3 副本 = 6 份。
  • 实际占用：200 MB × 3 = 600 MB（按实际字节算，不是按 3 × 256 MB）。
  • 写入交互：客户端要向 NameNode 要 2 次块位置（每块一次），每块建一条 3 节点的写入管道。

客户端与集群：两套机器、两条链路

这个模型能解释很多"为什么"。想象 深圳的客户端 连 北京的集群：

  • 控制面：客户端通过 RPC 连 NameNode 的 8020，问"我要读这个文件，块在哪些 DataNode 上"。
  • 数据面：拿到位置后，客户端直连 DataNode 的 9866 端口传字节。数据不经过 NameNode。

两个直接推论：① 客户端机器必须能解析所有节点的主机名（不然连不上 DN），这就是为什么 fs.defaultFS 不能写 localhost。② 客户端本地删除文件，不影响 HDFS 上的副本——两者本来就是两套系统。

1.8 跑通第一个作业，以及作业记录与回收站

用自带示例跑 MapReduce

hadoop jar share/hadoop/mapreduce/hadoop-mapreduce-examples-3.3.0.jar pi 10 100

四个部分拆开看：

片段含义
hadoop jar用 Hadoop 的 jar 提交器去跑一个 Java 包
...examples-3.3.0.jar要跑的 jar（版本号跟着自己集群走，可写 *）
pi主类名，这里是求圆周率
10map 任务数 —— 把大任务拆成 10 份
100每个 map 的采样点数

这两个数字决定结果准不准。课程演示时为跑得快用的是 pi 2 4（2 个 map、每个只采 4 个点），算出来是 3.5，离 3.14159 很远——这不是算错了，是样本太少。类比：调研全国平均工资，只抽 4 个人得出的结论当然不可信。

输出目录必须不存在——这是新手第一次跑 MR 最常见的失败。

pi 这个示例不写 HDFS 目录所以不会遇到，但同一个 jar 里的 wordcount、grep，以及你自己写的 MR，输出路径必须是一个不存在的目录：

FileAlreadyExistsException: Output directory hdfs://node1:8020/output already exists

原因是 Hadoop 用"目录创建成功"来保证这次输出是全新的、没被别的作业污染。处理只有两步：先删掉或换个路径，再重跑。

历史服务器：为什么需要它

不配会怎样？8088 上只能看到正在跑的作业，跑完就查不到了。因为作业结束后 ApplicationMaster 就退出了，运行时信息随之消失。JobHistoryServer 的作用就是把这些信息落盘并留存，供事后查看。

配置在 1.5 的 mapred-site.xml 里已经写好了（10020 + 19888 + 日志聚集）。这里补三个操作要点：

  1. 改完配置要 scp 分发并重启集群，配置不是热加载的。
  2. 历史服务器不在 start-all.sh 的管理范围内，必须单独启动：mapred --daemon start historyserver。这是最容易漏的一步——集群起来了但 19888 打不开。
  3. 验证地址：http://node1:19888。
一个反直觉的点：重启集群后，原有作业记录会清空。因为作业历史存在运行时的临时状态里，重启就没了。想让历史长期留存，得靠日志聚集把日志搬到 HDFS 上（yarn.log-aggregation-enable），这也是为什么 1.5 里那三项要一起配。

回收站：默认没有，开之前删了就是删了

HDFS 默认没有回收站。hdfs dfs -rm 相当于 Windows 的 Shift + Delete——执行时提示 Deleted /hello.txt，Web UI 里立刻消失，/user/root/.Trash 目录根本不生成。

生产环境必须开，原因一句话：HDFS 上的数据往往没有别的备份，一条 rm 敲错就是事故。

开启方式是改 core-site.xml（注意是核心配置，不是 hdfs-site.xml）：

<property>
    <name>fs.trash.interval</name>
    <value>1440</value>
</property>

三个要点：单位是分钟（不是秒也不是小时）；默认值 0 表示关闭；1440 = 24 小时，是生产常用值（课堂演示会改成 3 分钟好看到效果）。

改完同样要分发 + 重启。开启后删除的提示会变：

# 开启前
Deleted /hello.txt

# 开启后
Moved: 'hdfs://node1:8020/hello.txt' to trash at: hdfs://node1:8020/user/root/.Trash/current

看到 Moved 就说明进回收站了，文件还在，可以救。路径是 /user/<用户名>/.Trash/current，这个要背下来——出事的时候你会需要它。

收尾：这一章建立的三层认知

① 架构层：两个集群（HDFS + YARN）、六个角色、每台机器该有几个进程。判断几代看有没有 YARN。

② 操作层：六个配置文件 → format 一次 → start-dfs.sh → jps 对表 → 9870/8088 验收。出问题按"ERROR → jps → 手工启动 → 看日志"四步走。

③ 数据层：块是逻辑切分（128 MB 上限）、副本按机架放（1 本 + 2 跨）、小文件吃 NameNode 内存、客户端走两条链路（控制面 RPC、数据面直连 DN）。
