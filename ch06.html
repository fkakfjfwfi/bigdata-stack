06 · Hive 高级查询

这一章教三样"不会就写不出来"的东西：把一行拆成多行（explode + 侧视图）、把多行合成一行（行列转换）、在不聚合的前提下加汇总列（窗口函数）。三者的共同点是——语法都短，但用错方式不会报错，只是结果不对。窗口函数那部分尤其如此，一个默认窗口值能让你算出来的累计数全错。

内容基准 主体素材：Hadoop 实战课第 13 天（18 个有效视频，另有 1 个"回顾"和 1 个"扩展"已跳过）　·　2026-11 提炼 需留意：6.7 里 NTILE 那一集的音轨几乎无声（只转出开头 14 秒），该小节按 NTILE 标准语义整理并已核对，不是课程原话；其余各节均来自完整转写。窗口函数的默认窗口行为在各版本一致，可放心照用。

6.1 explode：一行变多行，以及它的硬限制

explode 是 UDTF（一行进、多行出），只能处理两种输入：

输入输出示例
array每个元素一行，单列["a","b"] → 两行
map每个键值对一行，两列（key, value）{"k1":1,"k2":2} → 两行两列
硬限制：SELECT 里不能同时出现 explode 和普通列。

下面这句直接报错，不是风格问题：

-- ❌ 报错
SELECT team_name, explode(championship_year) FROM nba;

原因：UDTF 返回的是一张"虚拟表"，里面只有炸出来的那一列。原表的 team_name 不在那张虚拟表里，没法一起 select。

解法就是下一节的 LATERAL VIEW——把原表和虚拟表关联起来。

（01 · 全篇）

6.2 LATERAL VIEW：三个名字别搞混

SELECT a.team_name, b.year
FROM the_nba_championship a
LATERAL VIEW explode(a.championship_year) b AS year;
位置是什么说明
a原表别名用来引用原表字段，如 a.team_name
b虚拟表别名（不是列名！）explode 生成的那张表的表名
AS year列别名虚拟表里那一列的名字；map 要写成 AS k, v

关联条件不用写 ON——侧视图会自动拿"被炸的那一列"和"炸出的每个值"做匹配。1991 出现在数组里，就把这条记录和 1991 拼成一行。

OUTER：空数组时的生死差别

这是本节最容易错、后果最隐蔽的一点。

默认的 LATERAL VIEW 是内连接语义——数组为 NULL 或空数组的行，整行会被丢掉。

-- 默认：空数组的行消失
SELECT a.id, b.tag FROM t a
LATERAL VIEW explode(a.tags) b AS tag;

-- OUTER：保留该行，tag 位置补 NULL
SELECT a.id, b.tag FROM t a
LATERAL VIEW OUTER explode(a.tags) b AS tag;

后果：对账类需求（"总用户数 = 各标签用户数之和"）如果忘了 OUTER，少几个空标签的用户，总数永远对不上，而且极难排查——因为 SQL 不报错。

判断标准很简单：这批数据的每一行都必须出现在结果里吗？是，就加 OUTER。

（03、07 两集）

6.3 行列转换：方向别搞反

这一节的核心是两个方向的记忆抓手：

名称形态变化本质手段
行转列（多行转单列）多行 → 一行（多列）聚合 / 收拢GROUP BY + collect_list + concat_ws
列转行（单列转多行）一行（多列）→ 多行展开 / 打散split + explode + LATERAL VIEW

口诀：收用聚合，散用 explode。

为什么别的函数不行

课程花了不少时间做排除，这个过程值得记，因为它解释了"为什么必须是这两个函数组合"：

尝试为什么不行
DISTINCT能去重，不能合并——1,2,3 还是三行
ROW_NUMBER()按分组取 rn=1，剩下的 2,3 直接丢了
GROUP BY能分组，但 SELECT 里只能放分组字段或聚合函数
concat不是聚合函数，放进 GROUP BY 的 select 里会报"字段不在 GROUP BY 中"

结论：必须先"把多行收集成数组"（聚合函数），再"把数组拼成字符串"（字符串函数）。两步缺一不可。

concat 与 concat_ws

SELECT concat('A', NULL, 'C');              -- NULL（任一为 NULL，整体 NULL）
SELECT concat_ws(',', 'hello', NULL, 'world');-- hello,world（自动跳过 NULL）
差别只有一条，但很致命：concat 遇 NULL 全盘皆输。

生产里拼字符串一律优先 concat_ws——它的第一个参数是分隔符，且自动跳过 NULL。用 concat 拼十个字段，只要有一个是 NULL，整列全变 NULL，而且不报错。

collect_list 与 collect_set

-- 数据：A,B,1 / A,B,2 / A,B,3 / C,D,4 / C,D,5 / C,D,6
SELECT collect_list(c1) FROM r2c2;   -- ["A","A","A","C","C","C"]  保留重复、有序
SELECT collect_set(c1)  FROM r2c2;   -- ["A","C"]                  去重、无序

选哪个看业务：要"用户看过哪些商品（含重复次数）"用 collect_list；要"用户涉及哪些品类（去重）"用 collect_set。

多行转单列：完整 SQL 与那个 CAST

SELECT
    c1,
    c2,
    concat_ws(',', collect_list(CAST(c3 AS STRING))) AS c3
FROM r2c2
GROUP BY c1, c2;
CAST(c3 AS STRING) 不能省。

建表时 c3 是 INT，collect_list(c3) 收回来是 array<int>——元素仍然是 int。而 concat_ws 只能拼字符串，喂 array<int> 直接类型不匹配报错。

这是 05 集里唯一的坑，也是这类写法最高频的报错。记忆：collect_list 会保留元素原类型，拼字符串前先 CAST。

单列转多行

-- 一行 "1,2,3" → 三行
SELECT a.id, b.v
FROM t a
LATERAL VIEW explode(split(a.vals, ',')) b AS v;

注意顺序：先 split 再 explode。字符串不能直接 explode，必须先切成数组——这是很多人第一次写时卡住的地方。

（04、05、06 三集）

6.4 JSON 三种处理方式

现在接口数据基本都是 JSON，这一节是日常用得最多的。三种方法各有明确适用面：

方法一次取几个字段能不能当表用适用场景
get_json_object1 个不能（普通 UDF，返回 STRING）只要少数几个字段；要把解析结果放进 WHERE / ORDER BY 做过滤排序
json_tuple多个能（UDTF，必须配 LATERAL VIEW）一次要拆 4~5 个字段，想把 JSON 变成"多列"
JSONSerDe全部列建表时就是表结构文件还没入表；最省事最快，一行一个 JSON 直接落地

get_json_object：$. 路径语法

SELECT get_json_object(json_str, '$.name')              -- 一级字段
SELECT get_json_object(json_str, '$.store.book[0].title') -- 嵌数组
SELECT get_json_object(json_str, '$.items[*].id')        -- 数组全部（返回 JSON 数组串）

json_tuple：一次多字段

SELECT a.id, b.name, b.age
FROM t a
LATERAL VIEW json_tuple(a.json_str, 'name', 'age') b AS name, age;

注意它不写 $.，直接给 key；列别名要和 key 数量对齐。

JSONSerDe：建表时就解析

CREATE TABLE t_json (
    name STRING,
    age  INT
)
ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.JsonSerDe'
STORED AS TEXTFILE;

-- 数据文件：一行一个完整 JSON，字段名与列名一致
-- {"name":"张三","age":20}
-- {"name":"李四","age":21}
选型判断：能改建表就用 JSONSerDe，不能改表就用 json_tuple，只要一两个字段做过滤就用 get_json_object。

按这个顺序选，基本不会错。反过来（一上来就 get_json_object 拆十个字段）会让 SQL 长到没法维护。

三者取不到值时都返回 NULL，不报错。

所以字段名大小写写错、路径写错，表现是"整列为空"而不是报错。遇到 JSON 解析后整列 NULL，先核对 key 的名字和层级，别怀疑数据。

6.5 窗口函数：OVER 里其实是三件事

先看它和 GROUP BY 的本质差别：

GROUP BY窗口函数
输出行数多行压成一行保留每一行原样
其他字段全丢（只能出现在聚合里）全部保留
典型用途统计汇总在明细旁边加一列汇总值（占比、累计、排名）

窗口函数的形态是 函数(...) OVER (...)，函数可以是聚合（SUM/AVG/COUNT）、排名（ROW_NUMBER）或分析（LAG/NTILE）。

OVER() 括号里能写三样东西，这是三件独立的事——90% 的结果不符预期都是漏了第三件。
子句管什么不写会怎样
PARTITION BY分几组（组内独立计算）整表当一组
ORDER BY组内怎么排（决定"前/后"是谁）无序，不能写 PRECEDING/FOLLOWING
ROWS / RANGE BETWEEN每行看多大范围默认 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

三种典型写法，记住它们的差别就掌握了八九成：

-- ① OVER() 空着 = 整表一个窗口
SELECT cookieid, pv, SUM(pv) OVER() AS total_pv FROM t;
-- 每行都挂上"全站总 PV"，用于算占比

-- ② 加 PARTITION BY = 每个用户一个窗口
SELECT cookieid, pv,
       SUM(pv) OVER (PARTITION BY cookieid) AS user_total
FROM t;
-- 每行挂上"这个用户的总 PV"

-- ③ 再加 ORDER BY = 组内累计（这才是最常见的用法）
SELECT cookieid, createtime, pv,
       SUM(pv) OVER (PARTITION BY cookieid ORDER BY createtime) AS running_total
FROM t;
-- 每行挂上"这个用户到这一刻为止的累计 PV"

边界术语

写法含义
UNBOUNDED PRECEDING组内第一行（往上到头）
UNBOUNDED FOLLOWING组内最后一行（往下到底）
n PRECEDING / n FOLLOWING往上 / 往下数 n 行
CURRENT ROW当前行本身

ROWS BETWEEN A AND B 里 A 是上界（更早）、B 是下界（更晚），写反直接报错。

（11、12、13 三集）

6.6 ROWS 与 RANGE：一个按行、一个按值

这是全章最容易错的地方，课程花了 13 分钟讲它，值得完整看一遍。

一句话分清：

ROWS 按物理行号框——只数"上几行、下几行"，跟值是多少完全无关。
RANGE 按 ORDER BY 那一列的值框——n PRECEDING 表示"值 ≥ 当前值 − n"。

一组实验数据看明白

表里只有一列 id，值是 1, 3, 5, 7, 9（奇数，不连续）。行号却是连续的 1~5——这个错位就是全部玄机。

SELECT id,
       SUM(id) OVER (ORDER BY id ROWS  BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS rows_sum,
       SUM(id) OVER (ORDER BY id RANGE BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS range_sum
FROM t1;
idrows_sumrange_sum为什么
141ROWS：上一行+自己+下一行 = 1+3；RANGE：值在 [0,2] 的只有 1
393ROWS：1+3+5；RANGE：值在 [2,4] 的只有 3（2 和 4 不存在）
5155ROWS：3+5+7；RANGE：[4,6] 只有 5
7217ROWS：5+7+9；RANGE：[6,8] 只有 7
9169ROWS：7+9；RANGE：[8,10] 只有 9

rows_sum 是标准的滑动窗口；range_sum 每一项都退化成"它自己"，因为相邻的偶数不存在。

并列值时差异才真正伤人

数据是 [1, 3, 3, 3, 5]，看中间那三个 3：

  • ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING：每个 3 只框自己 ±1 行，三个结果各不相同；
  • RANGE BETWEEN 1 PRECEDING AND 1 FOLLOWING：值区间是 [2,4]，三个 3 全在区间内，所以都拿到 3+3+3=9。
默认窗口是 RANGE，不是 ROWS。

有 ORDER BY 但没写 BETWEEN 时，默认是：

RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

这意味着——如果 ORDER BY 的列有并列值，这些并列行会一起被算进当前窗口。典型表现：按日期累计，同一天有 3 条记录时，三条记录的累计值都等于"这一天结束时"的总数，而不是逐条递增。

要严格逐行累加，必须显式写 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。

6.7 五个分析函数，各有一个坑

三大排名函数

函数并列序号两个 7 分并列第一时
ROW_NUMBER()不并列，硬拆连续1, 2, 3, 4
RANK()并列跳号1, 1, 3, 4
DENSE_RANK()并列不跳号1, 1, 2, 3

TopN 的写法在第 05 章 5.4 已经给过模板（WITH + 排名列 + WHERE rn = N），这里只补一句：要包含并列必须用 RANK 或 DENSE_RANK，用 ROW_NUMBER 会把并列的人硬拆成不同名次，那是业务错误而不是技术错误。

NTILE(n)：把数据切片

SELECT id, score,
       NTILE(4) OVER (ORDER BY score DESC) AS quartile
FROM t;

把分区内数据按顺序切成 n 份，返回桶号（1~n）。分不匀时前面的桶多一行——100 行分 3 份是 34/33/33，不是 33.3。典型用途：四等分算分位数、把用户按消费额分层做 AB 测试。

LAG / LEAD：取前/后第 n 行

SELECT dt, amount,
       LAG(amount, 1, 0) OVER (ORDER BY dt)  AS prev_amount,
       amount - LAG(amount, 1, 0) OVER (ORDER BY dt) AS diff
FROM t;

三个参数：取哪一列、往上几行、取不到时的默认值。第三个参数很关键——不写默认返回 NULL，第一行相减就是 NULL，整列计算跟着变 NULL。算同比环比、算两次行为的时间差，都靠它。

FIRST_VALUE / LAST_VALUE：那个必须知道的坑

-- ❌ 这样写，last_val 永远等于当前行的值
SELECT id, val,
       LAST_VALUE(val) OVER (PARTITION BY grp ORDER BY id) AS last_val
FROM t;
原因就是 6.6 那个默认窗口：RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。

窗口的右边界是"当前行"，LAST_VALUE 取窗口内最后一个值，那当然就是当前行自己。

正确写法必须显式把右边界推到组尾：

SELECT id, val,
       LAST_VALUE(val) OVER (
           PARTITION BY grp ORDER BY id
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS last_val
FROM t;

这一条不知道，会以为函数坏了。它和 6.6 是同一个知识点的两个表现——默认窗口的右边界只到当前行。

这一章的五条主线

① explode 线：一行变多行；不能与普通列同 select，必须配侧视图；空数组要加 OUTER 否则丢行。

② 转换线：收用聚合（collect_list + concat_ws），散用 explode（split 先切再炸）；CAST 别省。

③ JSON 线：能改建表用 JSONSerDe，只要几个字段用 get_json_object，一次拆多列用 json_tuple。

④ 窗口线：OVER() 三件事（分组 / 排序 / 范围）；默认窗口右边界只到当前行，这一条同时解释了 RANGE 的并列问题与 LAST_VALUE 的坑。

⑤ 判错线：这一章所有错误都不报错。看到"数量少了""累计值不对""最后一列等于当前行"，先回来看窗口范围和 OUTER。
