05 · Hive 查询操作

上一章把表建好了，这一章开始查。SQL 语法你大概都会，所以这章的增量不在"能不能写出来"，而在三件容易写错的事：四种排序的边界、JOIN 的 ON 与 WHERE 之别、以及 NULL 参与的每一次比较。这三处写错都不报错，只是结果不对——这是数据开发最典型的故障形态。

内容基准 主体素材：Hadoop 实战课第 12 天（23 个有效视频，另有 6 个 SQL 基础"回顾"已跳过）　·　2026-11 提炼 需留意：5.6 / 5.7 里"小表 25MB 阈值"和"非等值连接支持"都是 Hive 3.1.2 的行为，2.x 及更早版本不同（老资料说"Hive 只支持等值 join"就是指那个年代）；5.1~5.5、5.8~5.9 是 SQL 语义，不受版本影响。

5.1 四种排序：一个 Reducer 决定一切

Hive 有四个跟"排序"有关的关键字，名字像、行为完全不同。理解它们的唯一支点是这一句：

全局有序 ⇔ Reducer 数量为 1。

要让所有数据按某个字段整体排好，就必须把全部数据收到一个 Reducer 里排——这是数学上的必然，不是 Hive 的实现缺陷。四种排序的差异，本质就是"要不要收成一个 Reducer"。

关键字排序范围Reducer全局有序场景
ORDER BY全部数据强制 1 个✅结果集小的最终报表，必须配 LIMIT
SORT BY每个 Reducer 内部多个❌配 DISTRIBUTE BY 做可定制的区内排序
DISTRIBUTE BY不排序，只管分发多个（hash 取模）❌控制数据落点、缓解倾斜
CLUSTER BY同字段分区 + 区内升序多个❌（仅区内）恰好"按某字段分区又按同一字段升序"

一句话记忆：ORDER BY 是"一个锅炒所有菜"，慢但整齐；另外三个都是"分锅炒"，快但只在自己锅里整齐。

ORDER BY 的代价是具体的

数据量 1 亿行时，ORDER BY 会把 1 亿行全推到一个 Reducer。后果两种：内存撑不住直接 OOM，或者不报错但跑几十分钟不返回。所以生产上写 ORDER BY 几乎总要跟 LIMIT，让优化器有机会做"每个 Map 先取 TopN 再汇总"。

CLUSTER BY = DISTRIBUTE BY + SORT BY（同一个字段）

-- 这两句在"分区字段 = 排序字段且升序"时等价
SELECT * FROM student CLUSTER BY sex;

SELECT * FROM student DISTRIBUTE BY sex SORT BY sex;
CLUSTER BY 有两个硬限制，一碰就得拆开写：

① 只能升序——CLUSTER BY age DESC 会报语法错。
② 分区字段和排序字段必须是同一个。

所以需求一旦变成"按性别分区、按年龄降序"，CLUSTER BY 就做不到，必须用下面的组合。

（06、07 两集）

5.2 DISTRIBUTE BY + SORT BY：把两件事拆开

SET mapreduce.job.reduces = 2;      -- 两个区，方便观察

SELECT *
FROM student
DISTRIBUTE BY sex                 -- 男生进一个 Reducer、女生进另一个
SORT BY age DESC;                -- 每个 Reducer 内部按年龄降序

实际效果：男生整块在一起、女生整块在一起，各自内部按年龄降序。但两块之间没有任何全局顺序——男生 21 岁后面可能跟着女生 22 岁，这完全正常。

需求用什么
同字段分区 + 区内升序CLUSTER BY（最简）
要降序，或分区字段 ≠ 排序字段DISTRIBUTE BY ... SORT BY ...
要全局有序ORDER BY（+ LIMIT）
DISTRIBUTE BY 有个容易被忽略的用途：缓解数据倾斜。

它决定"哪行去哪个 Reducer"（默认 hash 取模）。如果某个 key 特别多导致单个 Reducer 卡死，可以在这里加随机前缀把热点打散，再在下一层聚合回来。这条思路在第 07 章的 MR 优化里还会遇到。

（08 · 全篇；倾斜用途为补充）

5.3 UNION 与 CTE：拼接和命名

-- UNION ALL：只拼接，不去重，快
SELECT * FROM t1
UNION ALL
SELECT * FROM t2;

-- UNION：等价 UNION DISTINCT，去重（要走 shuffle）
SELECT * FROM t1
UNION
SELECT * FROM t2;

差别只有一句：UNION 去重、UNION ALL 不去重。代价是去重必须把数据集中比较，走一轮 shuffle。生产上默认写 UNION ALL，需要去重时再显式套一层 DISTINCT 或 GROUP BY——这样"哪里要付去重的代价"是你看得见的。

两个约束：上下两段的列数必须相同、对应列的类型必须兼容（否则报错或静默转 NULL）；列名以上面那段为准。UNION 是纵向拼行，跟 JOIN 的横向拼列是两回事。

CTE：给中间结果起个名

WITH tmp AS (
    SELECT country, city, score FROM shop
)
SELECT * FROM tmp WHERE score > 7;

等价于嵌套子查询，但可读性差一个量级。CTE 的价值在长 SQL 里：把"中间结果"提到最前面命名，一层逻辑一段。TopN 那种"排名一层、筛选一层"的题，不用 CTE 会写成三层嵌套，改起来要命。

（09 · 全篇；10 前半）

5.4 TopN：为什么不能直接 ORDER BY + LIMIT

题目：shop(country, city, score)，求每个国家评分最高的门店。

直觉写法 ORDER BY score DESC LIMIT 1 有两个问题：

  • 它只能拿全局第一（深圳 9 分），而要的是每个国家各自的第一名。
  • 就算只求全局第一，ORDER BY 也是单 Reducer 全排，大数据量下 OOM 或几十分钟不返回。

三个排名函数，别选错

函数并列时序号示例（两个 7 分并列第一）
ROW_NUMBER()不并列，硬拆开连续1, 2, 3, 4
RANK()并列跳号1, 1, 3, 4
DENSE_RANK()并列不跳号1, 1, 2, 3

选法很明确：取第一名三个都行；取前 N 名且要包含并列必须用 RANK 或 DENSE_RANK；取恰好 N 条（不管并列）用 ROW_NUMBER。

标准解法：三段式

WITH temp AS (
    SELECT country,
           city,
           score,
           ROW_NUMBER() OVER (PARTITION BY country ORDER BY score DESC) AS rn
    FROM shop
)
SELECT city
FROM temp
WHERE rn = 1;

结构就是三段：① 子查询里加一列排名 → ② 外层 WHERE rn = 1 筛 → ③ 只取需要的列。PARTITION BY 决定"按什么分组"，ORDER BY score DESC 决定"组内谁第一"。

要保留并列第一（法国巴黎和波尔多都是 7 分），把 ROW_NUMBER() 换成 RANK() 即可，条件仍是 rn = 1。这就是上面那张表说的区别——同一个模板，换个函数就换了语义。

（10 · 全篇）

5.5 六种 JOIN 一张表看完

类型保留哪边不匹配时用途
CROSS JOIN两边全留，逐行两两配对（m×n 行）——造全组合维度（日期×门店）；业务里几乎不用
INNER JOIN（默认）只留两边都匹配上的整行丢弃绝大多数关联取数
LEFT [OUTER] JOIN左表全留 + 右表匹配部分右侧字段置 NULL以主表为基准挂维表，允许维表缺失
RIGHT [OUTER] JOIN右表全留左侧置 NULL同上，工程上一般调换顺序写 LEFT
FULL [OUTER] JOIN两边全留缺的那侧置 NULL双向对账，找"只在 A 有 / 只在 B 有"
LEFT SEMI JOIN只留左表匹配上的行，且只输出左表字段丢弃；右表列一律不出现Hive 特有，替代 IN / EXISTS 做"是否存在"过滤，更快

记法：CROSS 全要、INNER 要交集、LEFT/RIGHT/FULL 各留一边或两边、SEMI 只留左表还只出左表。

Hive 只有 LEFT SEMI JOIN 这一种 SEMI，写 RIGHT SEMI JOIN 或 FULL SEMI JOIN 直接语法错误。

为什么 LEFT SEMI JOIN 比 IN 快？

因为它只需要判断"右表有没有匹配"，不需要把右表的列取出来。右表只做匹配探测，可以在 Map 端完成，省掉一轮 shuffle。而 IN (子查询) 在 Hive 里可能被改写成 JOIN 再去重，代价高得多。

（11~16 六集）

5.6 三个硬坑：ON/WHERE、NULL、Map Join

坑一：外连接时 ON 与 WHERE 完全不是一回事

内连接里，条件写 ON 还是 WHERE 结果一样（优化器会下推）。外连接里语义截然不同：

-- ① 条件在 ON：左表 4 行全在，不满足条件的右侧字段补 NULL
SELECT e.id, e.name, ea.city
FROM employee e
LEFT JOIN employee_address ea
       ON e.id = ea.id
      AND ea.city = '北京';

-- ② 条件在 WHERE：补 NULL 的行被筛掉 → 退化成 INNER JOIN
SELECT e.id, e.name, ea.city
FROM employee e
LEFT JOIN employee_address ea
       ON e.id = ea.id
WHERE ea.city = '北京';
根源是执行顺序：JOIN 先算完，WHERE 再对结果过滤。

JOIN 算完时，没匹配上的行 ea.city 已经是 NULL。然后 WHERE 判断 NULL = '北京'——结果是 UNKNOWN，不是 true，整行被丢掉。

口诀：想"保留主表全部行、只让不满足条件的关联字段变 NULL"→ 写 ON；想"真的把不满足条件的行删掉"→ 写 WHERE。

这是线上事故和面试的双料高频点。很多人写完左连接发现"怎么变成内连接的结果了"，就是这一条。

坑二：JOIN 键为 NULL 的行永远匹配不上

NULL = NULL 在 SQL 里不是 true，是 UNKNOWN。所以两张表里都是 NULL 的 key 也关联不上，那些行直接消失。

后果：对账时数量对不上，但你怎么查都找不到丢在哪。防御办法是在 JOIN 前先处理 NULL：

SELECT *
FROM a
JOIN b ON NVL(a.k, '__NULL__') = NVL(b.k, '__NULL__');

或者干脆在 ETL 阶段就把 NULL 填成明确的默认值，别让它流到关联层。

坑三：小表 join 大表，顺序写反 Map Join 就失效

小表能装进内存时，Hive 会把它广播到每个 Map 节点，直接在 Map 端完成 join，完全省掉 reduce 端 shuffle——这叫 Map Join，是最有效的单点优化之一。

项值
开关hive.auto.convert.join（3.x 默认开）
小表阈值hive.mapjoin.smalltable.filesize，默认 25 MB
写法要求小表写在前面（FROM 小表 JOIN 大表）
强制指定/*+ MAPJOIN(小表别名) */
顺序写反了 Map Join 直接失效，而且不报错——它会静默退化成普通的 reduce join，你只会觉得"怎么这么慢"。不确定时用 hint 强制指定：
SELECT /*+ MAPJOIN(dim) */ f.id, dim.name
FROM fact f
JOIN dim ON f.dim_id = dim.id;

5.7 非等值连接、多表同键与数据倾斜

非等值连接：3.x 能跑，但不该跑

老资料常说"Hive 只支持等值 join"，那是 1.x 年代的结论。Hive 3.x 已经支持非等值条件：

-- 3.x 可执行（1.x 会报错）
SELECT *
FROM employee e
JOIN employee_address ea ON e.id <> ea.id;
"能跑"不等于"该跑"。

非等值条件无法用哈希定位，执行计划会退化成"笛卡尔积 + 过滤"——两张 10 万行的表先乘出 100 亿行再筛，数据量一大就是灾难。

正确做法：非等值逻辑挪到 WHERE，或者先用 CASE WHEN 把区间打标成一列，再做等值关联。

多表 JOIN 时，相同连接列会合并成一个 MR

如果三张表都按同一个 key 关联，Hive 会把它们合并到同一个 MapReduce 作业里完成，而不是串成三个作业。省掉两轮 shuffle。

怎么验证：去 8088 的作业历史里看 Maps / Reduces 数量——如果三表 join 只有一个作业，说明合并成功了。这个技巧在调优时很好用：作业数比预期多，说明优化没生效。

数据倾斜：单个 Reducer 卡在 99%

怎么识别：8088 里看到大部分 reduce 已经完成，剩一两个卡在 99% 长时间不动；或者某个 task 的输入记录数远超其他。

成因：某个 key 特别多（NULL、空串、默认值 -1、某个爆款商品）。hash 之后全落到同一个 Reducer。

手法做法适用
先过滤把 NULL / 空串 / 默认值这些异常 key 剔掉，单独处理首选，最简单
Map Join小表广播，绕开 reduce有一侧是小表
打散加盐热点 key 加随机前缀（key_0~key_9），聚一次再合并热点无法过滤时
单独处理热点 key 拎出来单独跑一个作业，结果 union 回去热点极少但极大
排查顺序建议：先看是不是 NULL 造成的。很多"倾斜"其实是几百万行 NULL 全落到一个 Reducer，过滤掉就正常了——这比加盐简单得多，也更快见效。

5.8 参数配置与 NULL 比较

参数的三级优先级

层级写法生效范围优先级
配置文件hive-site.xml永久最低
启动参数hive --hiveconf k=v本次会话中
会话内SET k=v;当前会话，断开即失效最高
 
SET hive.exec.dynamic.partition;        -- 查单个参数当前值
SET -v;                              -- 查全部（输出很长）
"参数为什么不生效"的第一怀疑对象：被上层覆盖了。

你在 hive-site.xml 改了一个值，但启动脚本里带了 --hiveconf 覆盖它，或者前面某个脚本已经 SET 过了。先用 SET k; 看实际值，再改。

NULL 比较：最反直觉的一块

SQL 里 NULL 不是"空值"，是"未知"。任何与 NULL 的比较结果都是 UNKNOWN，而 WHERE 只保留结果为 true 的行。于是：

SELECT * FROM t WHERE col != 'x';    -- 漏掉 col 为 NULL 的行！
SELECT * FROM t WHERE col NOT IN ('x', NULL); -- 直接返回空集
第二条尤其隐蔽：NOT IN 的列表里只要有一个 NULL，整个条件永远不成立，返回空集。

因为 col NOT IN ('x', NULL) 展开是 col <> 'x' AND col <> NULL，后半段恒为 UNKNOWN，AND 之后就恒不成立。

所以子查询结果作为 IN 列表时，一定要先 WHERE col IS NOT NULL。

三个专门对付 NULL 的函数：

函数行为典型用法
NVL(a, b)a 为 NULL 时返回 b，否则返回 a给缺失值兜底
COALESCE(a, b, c)返回第一个非 NULL多级兜底（手机号→座机→邮箱）
NULLIF(a, b)a = b 时返回 NULL，否则返回 a把"0 表示缺失"转成标准 NULL

还有一个 null-safe 等号 <=>：NULL <=> NULL 返回 true。它就是为"我要让 NULL 和 NULL 相等"这个场景准备的，比套一堆 NVL 干净。

（18、19、21、27 四集；<=> 与 NULLIF 为补充）

5.9 函数速查

函数分三类，判断标准是输出行数，不是返回类型：

类别输入 → 输出例子
UDF（普通函数）一行 → 一行substr、concat、split（返回数组但仍是一行）
UDAF（聚合函数）多行 → 一行sum、count、collect_list
UDTF（表生成函数）一行 → 多行explode、json_tuple

最容易判错的是 split——它返回数组，看着像"一行变多"，但只要不配 explode，输出仍然是一行，所以它是 UDF。

字符串

函数作用示例
concat(a, b, ...)拼接（任一个为 NULL 则整体 NULL）concat('a','b') → ab
concat_ws(sep, ...)带分隔符拼接，自动跳过 NULLconcat_ws('-','a',NULL,'b') → a-b
substr(s, start, len)截取，下标从 1 开始substr('abcde',2,3) → bcd
length(s)长度length('abc') → 3
upper / lower大小写upper('ab') → AB
trim / ltrim / rtrim去空格trim(' a ') → a
split(s, regex)按正则切分成数组split('a,b',',') → ["a","b"]
regexp_replace(s, pat, rep)正则替换regexp_replace('a1b','[0-9]','') → ab
instr(s, sub)子串位置（找不到返回 0）instr('abc','b') → 2
lpad / rpad左右补齐lpad('5',3,'0') → 005

日期时间

函数作用
current_date() / current_timestamp()今天 / 此刻
unix_timestamp([s, fmt])字符串 → 秒级时间戳
from_unixtime(ts, fmt)时间戳 → 字符串
date_format(d, fmt)格式化日期
date_add(d, n) / date_sub(d, n)加 / 减 n 天
datediff(d1, d2)相差天数

last_day(d)当月最后一天（算月维度常用）
格式符大小写敏感：yyyy-MM-dd HH:mm:ss 里的 MM（月）和 mm（分）不是一回事，HH 是 24 小时制、hh 是 12 小时制。写错不报错，只是结果错。

复杂类型与数学

函数作用

脱敏与摘要

函数用途
mask_first_n(s, n) / mask_last_n遮蔽前 / 后 n 位（手机号、身份证）
mask_hash(s)返回哈希串，可逆性为零但保留可关联性
md5(s) / sha1(s) / sha2(s, n)摘要，不可逆

脱敏的两种思路要分清：要保留"同一个人还是同一个人"的关联能力 → 用哈希（同一输入永远同一输出）；只要看不清原文 → 用 mask 遮蔽。

这一章的四条主线

① 排序线：全局有序 ⇔ 单 Reducer。要全局就 ORDER BY + LIMIT，要分区内有序就 DISTRIBUTE BY + SORT BY。

② 连接线：六种 JOIN 记住"留哪边、怎么补"，SEMI 是 Hive 特有且更快。外连接里 ON 保行、WHERE 删行。

③ NULL 线：!= 漏 NULL、NOT IN 遇 NULL 返空集、JOIN 键为 NULL 永不匹配、LAST_VALUE 默认窗口只看当前行。所有"结果数量不对"的问题，先查 NULL。

④ 优化线：小表在前走 Map Join、多表同键合并单 MR、倾斜优先查 NULL 而不是加盐。
